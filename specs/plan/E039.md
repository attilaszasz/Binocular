# Epic Details: E039 — Catalog Release Readiness

- **Category**: OPERATIONAL
- **Priority**: P1
- **Source**: {PRD:CAP-009}{SAD:ADR-0015}{SAD:ADR-0016}{SAD:ADR-0017}{DOD:DDR-005}

## Scope
Integrate deterministic catalog-first CI/readiness validation and operator guidance across the already implemented E032–E038 contracts. Rehearse populated upgrades, restart/restore/rollback, source partial/failure recovery, and definite versus uncertain delivery retry without changing deployment topology or treating this bootstrap amendment as a shipped implementation.

- **Actors**: Operator, maintainer
- **Key Entities**: Schema/backup version, catalog/inventory associations, module controls/capabilities, refresh/fan-out cursors, delivery intent/attempt/history
- **Depends on**: E032, E033, E034, E035, E036, E037, E038, E003, E017, E018
- **Dependency Contracts**: Complete catalog/contract/official-source/shared-loop/UI increment; existing multi-arch container CI/release scanning and live-safe backup/restore; DOD DDR-005 operations/readiness requirements
- **Depended on by**: None
- **Produces (shared)**: Integrated fixture/network-isolation/accessibility/performance/consistency gates; packaged contract/kit parity checks; populated upgrade/restart/restore/rollback rehearsal evidence; catalog/legacy/source/delivery operator runbooks and release notes
- **Constraints**: Same single non-root container/port/SQLite/modules volumes, no cloud/broker/external telemetry, no live manufacturers or real sleeps in mandatory validation. Each prior epic owns its own correctness tests; this epic integrates them rather than deferring missing functionality. Release readiness requires actual successful validation, never documentation-only markers.

## Acceptance Criteria
- [ ] CI enforces instructions v2.0.0, 80% coverage, lint/strict typing/security, accessibility and bounded performance, plus all official captured-fixture/contract/kit parity tests. Integrated smoke covers zero-inventory discovery, shared index/per-model details, successful/partial/failed/stale refresh, both catalog onboarding entry points with unknown installed and multiple copies, local-only interaction against 10,000 models, and independent per-device comparison/alerts.
- [ ] Populated upgrade and failure recovery prove backup-gated offline additive migration, preserved device/module/model identity, installed/unknown/history/controls, exact-only linking, V1 legacy operation, and explicit unresolved migration. Restart recovers valid bounded work without budget-reset loops or stale-worker writes; restore/rollback uses matching schema and compatible custom modules, preserves data boundaries, and reconciles possibly already-delivered restored intents before dispatch resumes.
- [ ] HTML Email/SMTP and Gotify tests cover canonical concurrent/repeated deduplication, channel-specific definite failure/retry without successful-channel resend, displayed-target confirmation races, interrupted/uncertain send visibility and warned explicit retry, and no automatic uncertain replay after crash or restore. State clearly that app deduplication is not universally exactly-once external delivery and an accepted in-flight alert cannot be recalled.
- [ ] Ship operator run/upgrade/restore/rollback/source/notification incident guidance and version-aligned README/authoring/harness/templates/AI Kit assets. Explain local global scope, zero-inventory egress, module-wide pause/frequency, bounded progress/partial failures, separate endpoint TTL versus observation age, no latest-as-installed assumption, V1 migration/fallback, Canon verified exclusions, and definite/uncertain retry. Validate the same image/port/volumes/non-root behavior; record real results and unresolved release blockers without publishing or deploying automatically.
