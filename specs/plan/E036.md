# Epic Details: E036 — Shared Comparison and Durable Alerts

- **Category**: PRODUCT
- **Priority**: P1
- **Source**: {PRD:CAP-006}{PRD:CAP-007}{PRD:CAP-010}{PRD:CAP-014}{SAD:ADR-0017}{DOD:DDR-005}

## Scope
Use one local comparison path for successful shared model refresh and device add/edit/update confirmation, with bounded durable fan-out to every linked physical device. Replace race-prone notification suppression with durable per-device/version/channel intents and exclusive delivery, preserving Email/SMTP/Gotify, independent device state, visible failure, and safe retry/uncertainty handling.

## Traceability & Dependencies
- **Actors**: Operator, comparison worker, notification worker
- **Key Entities**: Device revision/installed-unknown, FirmwareObservation generation, ReevaluationWork, NotificationIntent, channel delivery attempt/watermark, module refresh health
- **Depends on**: E032, E033, E034, E010, E014, E015, E020, E021
- **Dependency Contracts**: E032 caller-owned transaction/write primitives and unique intent persistence; E034 atomic observation/reevaluation enqueue and run status; existing source-aware version comparator, HTML email/Gotify channels, environment settings, activity view, official module health
- **Depended on by**: E037, E038, E039
- **Produces (shared)**: Shared comparison/fan-out service, atomic device mutation/confirmation hooks and payloads, durable outbox/claims, channel retry/status actions, correlated activity and zero-inventory refresh health
- **Constraints**: No network inside transactions or duplicate enqueue/concurrent sends; no external exactly-once promise. Preserve delivered history/installed state/module controls and independent device identity. E035 may run in parallel only with frozen E032–E034 contracts and separate files/tests.

## Acceptance Criteria
- [ ] Successful authoritative model verification drains durable bounded fan-out to every linked device; add/installed edit/confirmation atomically save revision plus work for the same local comparison without vendor requests. Concurrent new/changed devices cannot be lost behind a refresh cursor; generations/revisions reject obsolete completions while retaining successor reevaluation.
- [ ] The existing reliable source-aware comparator governs latest/installed and newer-than-notified ordering with canonical equivalent-version keys, never lexical guesses. Explicit unknown installed and incomparable values never yield current; stale/failed/unavailable data stays labeled and cannot establish new current/alert claims. Multiple physical devices keep independent state, and only fresh verified firmware newer than installed and the channel's delivered watermark qualifies.
- [ ] One-click confirmation records exactly the displayed target version/observation ID using expected device revision, visibly rejects conflicts, supersedes obsolete unsent alerts, and reevaluates without erasing delivered history. Standard device add/edit APIs enforce stable catalog/module linkage, explicit unknown/version input, and the same mutation hooks needed by both UI entry points.
- [ ] Atomic unique device/canonical-version/channel intents, bounded fan-out commits, exclusive claim tokens/generations, and compare-and-set outcomes prevent duplicate application enqueue/concurrent dispatch across repeated refreshes/actions/restarts. Sending occurs outside transactions after a current-revision/eligibility check; lease expiry cannot start a second live sender. Deterministic races cover refresh versus add/edit/confirm, stale workers, channel completion, and crash boundaries.
- [ ] Definite Email/SMTP or Gotify failure stays visible/retryable through the same channel intent without resending successful channels; per-channel history cannot be suppressed by an aggregate last_notified_version. Ambiguous/interrupted sends become uncertain with no automatic replay and an explicitly warned manual retry. Accepted-send evidence survives concurrent edits; expose the unavoidable already-accepted-message boundary. Structured activity/status and official health include zero-inventory refreshes and distinguish no-firmware from failure; legacy V1 alerts continue to use safe deduplication.

## Specify Input
- **Description**: Compare shared model firmware observations against every linked owned device, also reevaluating locally on creation, installed-version edit, and explicit displayed-target update confirmation. Preserve source-aware version correctness and unknown/stale/failure honesty. Use bounded transactional fan-out and durable unique device/version/channel notification intents with exclusive claims, revision/generation fencing, preserved delivery history, HTML Email/SMTP and Gotify, visible definite failure/retry and uncertain-delivery handling. Repeated/concurrent refreshes and user actions must not duplicate application alerts or resend successful channels; do not claim externally guaranteed exactly-once delivery.
- **Actors**: Operator, comparison worker, notification worker
- **Key Entities**: Device, FirmwareObservation, ReevaluationWork, NotificationIntent/attempt, channel watermark, refresh health
- **Depends on Artifacts**: E032 write ownership and durable schema, E033 V1/V2 descriptor, E034 successful-observation work/status, existing comparator/channels/config/activity/health; ADR-0017 dispatch/recovery boundaries
- **Constraints**: No vendor request for local reevaluation; unknown never current; only fresh verified versions alert; preserve history; no network in transactions; same shared mutation behavior for both creation entry points; no automatic uncertain-send retry or claim stealing from live senders.
