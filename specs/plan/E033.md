# Epic Details: E033 — Catalog Contract and V1 Compatibility

- **Category**: TECHNICAL
- **Priority**: P1
- **Source**: {PRD:CAP-002}{PRD:CAP-003}{PRD:CAP-013}{SAD:ADR-0016}

## Scope
Introduce an explicitly negotiated catalog-capable module protocol for separate enumeration and firmware retrieval, with shared-index and per-model-detail support. Preserve valid V1 custom modules as visibly non-enumerating, and align loader/validation, lifecycle safety, authoring documentation, harness, templates/examples, and AI Module Kit with the same contract.

## Traceability & Dependencies
- **Actors**: Module author, operator, maintainers, AI-assisted module author
- **Key Entities**: ModuleContractDescriptor, CatalogPage, FirmwareResult, host refresh context, ModuleValidationResult, CatalogModel
- **Depends on**: E032, E007, E009, E019, E022, E030
- **Dependency Contracts**: E032 stable variant/observation mappings and transaction-aware module persistence; existing loader, two-phase validator/progress stream, module lifecycle, source guidance, and downloadable authoring assets
- **Depended on by**: E034, E035, E037, E038, E039
- **Produces (shared)**: V2 result/context schemas and callable contract; negotiated module API/capability descriptor exposed locally; labeled V1 adapter; capability-aware validation/progress/errors; coherent V1-to-V2 migration guide and kit/harness/templates
- **Constraints**: MODULE_VERSION is not protocol version. No undeclared enumeration, new mandatory V2 metadata on valid V1, or fallback for unsupported declared versions. Preserve unsandboxed in-process/non-root trust boundary, centralized client/deadlines, module/model identities, saved controls, and referenced inventory on update/delete.

## Acceptance Criteria
- [ ] Missing MODULE_API_VERSION or explicit integer 1 selects V1 check_firmware(url, model, http_client); V2 catalog requires integer 2 plus MODULE_CAPABILITIES containing catalog. Unsupported/malformed declarations and V1/catalog contradictions fail with structured copyable validation errors rather than silently falling back; callable presence alone never grants catalog support.
- [ ] V2 discover_models(http_client, context) returns host-validated CatalogPage entries with stable source/variant identity, names/aliases/links and explicit continuation/completeness; optional authoritative inline firmware and required get_firmware(model, http_client, context) cover shared-index and per-model-detail sources. Host-scoped context provides bounded cursor/deadline/cancellation and response reuse; fixtures distinguish successful discovery, verified firmware/no-firmware, partial scan, identity ambiguity, and source failure.
- [ ] AST and optional explicit runtime proof validate negotiated signatures/results and report real progress without claiming a sandbox. Valid V1 manual entry, explicit per-model checks, and legacy owned-device scheduling remain functional and labeled unsupported-catalog. Same-ID updates/seeding preserve controls/associations; referenced module deletion and capability downgrades cannot silently orphan inventory. An unresolved migrated device uses a V1 checker only when actually retained, otherwise needs model selection.
- [ ] README/authoring documentation, local validation harness, contract reference, starter/working example, downloadable AI Module Kit instructions/assets, and AI-friendly errors agree on V2 capability, stable variants, shared indexes/details, partial/failure/freshness behavior, and V1 migration. Tests cover legacy uploads and both versions' assets/results without manufacturer requests from simply opening guidance or validator UI.

## Specify Input
- **Description**: Define explicit module API version and catalog capability negotiation independently of author revision. Add separate model enumeration and identity-matching firmware retrieval using host-owned bounded shared context, with authoritative optional inline results and per-model detail retrieval. Preserve existing V1 custom monitoring as labeled manual-entry/per-model fallback, not invented enumeration. Keep lifecycle validation, source help, identity/control safety, authoring documentation/harness/templates/examples and AI Module Kit coherent, with an actionable migration path from verified source enumeration through stable variant keys/fixtures to explicit V2 activation under the same module ID.
- **Actors**: Module author, operator, maintainer, AI-assisted author
- **Key Entities**: ModuleContractDescriptor, CatalogPage, FirmwareResult, RefreshContext, ModuleValidationResult
- **Depends on Artifacts**: E032 persistence and write ownership; E007/E009/E019/E022/E030 loader/lifecycle/progress/authoring/source guidance; ADR-0016 canonical protocol
- **Constraints**: No source calls from passive UI/asset access, no silent V1 breakage or capability inference, all requests through the host client, unsandboxed trust stated honestly, legacy identity/history and module controls preserved.

## Pipeline Hints
- Keep capability/result/context schemas stable before E034/E035; do not skip migration/compatibility validation.
