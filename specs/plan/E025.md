# Epic Details: E025 — Official Viltrox Lenses Module

- **Category**: PRODUCT
- **Priority**: P2
- **Source**: {PRD:CAP-011}{SAD:ADR-0005}

## Scope
Ship a new official starter module `viltrox_lenses` for Viltrox lens firmware detection. Viltrox publishes firmware on a Shopify-hosted site with a two-step flow: an index page listing ~70 lenses across 6 mount groups (FE / E / X / Z / M / DL), each linking to its own lens page; each lens page lists firmware releases under a `### Document Download` section as `<lens name> V<version>` entries (e.g. `TC-2.0X FE V1.03`), with the top entry being the latest. The module must follow the existing authoring contract (ADR-0005) and pass fixture-based correctness validation.

## Problem Statement
Photographers using Viltrox lenses (a popular third-party manufacturer across multiple camera mounts) have no native way to monitor firmware updates through Binocular. The application ships official starter modules for several other manufacturers (Sony Alpha, Panasonic Lumix MFT, Panasonic Lumix Lenses, Godox Flashes) and the CAP-011 capability covers the shipped-official-modules surface, but Viltrox support is missing. Operators must currently hand-author a Viltrox module against a custom flow (Shopify /pages/ links + per-lens download sections), which fragments the value of an otherwise plug-and-play starter set.

## Traceability & Dependencies
- **Actors**: Operator (consumer)
- **Key Entities**: Viltrox Lenses official module file, lens page index, lens page `### Document Download` section entries
- **Depends on**: E007 (module engine + contract), E011 (Sony Alpha module pattern), E016 (module seeding)
- **Dependency Contracts**: E007 authoring contract (`check_firmware(url, model, http_client)` returning a `latest_version` dict; `MODULE_VERSION` constant; `SUPPORTED_DEVICE_TYPE` constant); E005 ScrapeClient
- **Depended on by**: E020 (official module health monitoring)
- **Produces (shared)**: `backend/src/binocular/official_modules/viltrox_lenses.py`, fixture/captured-page test files
- **Constraints**: Authoring contract; golden/fixture-based correctness tests; idempotent auto-seeding; no use of any SDK outside the host-provided ScrapeClient

## Demo Plan
- Run the dev environment with the `viltrox_lenses` module seeded automatically on startup.
- From the inventory page, create a device linked to the `viltrox_lenses` module using model `TC-2.0X FE` (or any fixture-backed lens).
- Trigger a manual on-demand check; observe the detected `latest_version` matches the fixture's top `### Document Download` entry.
- Update the stored version to an older value and re-check; observe a newer-version detection and a notification.
- Run the Playwright end-to-end smoke test and the module's pytest fixture suite against a captured Viltrox index page + a captured lens page to confirm zero false positives / zero false negatives.

## Draft Scenarios / Objectives
- **S1 — Module discovery and auto-seeding**: On application startup, the seeder discovers `viltrox_lenses.py` in `official_modules/`, validates it (Phase 1 AST + Phase 2 runtime), and upserts the module record in SQLite without duplicating on re-runs.
- **S2 — Two-step flow (index → lens page)**: For a configured lens model, the module fetches the index page `https://viltrox.com/pages/download-center-1`, locates the per-lens `/pages/<slug>` link that matches the requested model, follows the link, and parses the lens page.
- **S3 — Firmware version extraction**: From the `### Document Download` section of the lens page, the module extracts the top entry's `<lens name> V<version>` (e.g. `TC-2.0X FE V1.03`), normalizes the version (stripping a leading `V`), and returns it as `latest_version`. The first entry is treated as latest; remaining entries are not required.
- **S4 — Companion app version filtering**: The module must not interpret the companion app version (e.g. `Viltrox Lens V1.13 for Mac/Win`) as a lens firmware version. Only entries inside `### Document Download` on a per-lens page are valid; index-page companion app mentions are ignored.
- **S5 — Model key resolution**: The module accepts the lens display name (e.g. `TC-2.0X FE`) as the model key, with the page slug as a fallback when the display name does not match an index entry directly.
- **S6 — Honest failure**: Page-structure changes (e.g. section renamed, no entries found) produce a visible "scrape failed" status with a descriptive error code (e.g. `parse_error`, `product_not_found`, `firmware_not_available`), never a silent miss.

## Integration Points
- **Module engine (E007)**: Implements `check_firmware(url, model, http_client)`, declares `MODULE_VERSION` and `SUPPORTED_DEVICE_TYPE = "lens"`.
- **ScrapeClient (E005)**: All outbound HTTP goes through the host-provided polite httpx client (robots.txt, identifiable User-Agent, rate limiting, backoff). No direct outbound requests.
- **Module seeder (E016)**: The seeder auto-discovers `viltrox_lenses.py` in `official_modules/` on startup and upserts it into the modules table alongside the existing four official modules.
- **Notification flow (E014)**: When a newer version than the user's recorded version is detected, the same Apprise dispatch path delivers an HTML Email/SMTP and/or Gotify alert. Deduplication via `last_notified_version` still applies.
- **Activity log (E015)**: Successful and failed check events for Viltrox devices land in the in-UI activity log just like any other module.
- **Official module health monitoring (E020)**: A Viltrox device whose checks consistently fail will surface in the in-app "official module failing" notification alongside other official modules.
- **Version search on creation (E023)**: When the operator uses the on-demand "search version" button while creating a Viltrox device, the existing `/api/v1/checks/search-version` endpoint delegates to the module runner with the new module.

## Implementation Signals
- New file: `backend/src/binocular/official_modules/viltrox_lenses.py`
- Constants: `MODULE_VERSION = "1.0.0"`, `SUPPORTED_DEVICE_TYPE = "lens"`
- Entry point: `check_firmware(url: str, model: str, http_client: Any) -> dict[str, Any]`
- Returned dict shape (matching the existing official modules):
  - `latest_version` (str, required) — top entry version, `V` prefix stripped
  - `release_date` (str | None) — date string from the same top entry, when present
  - `download_url` (str) — download link associated with the top entry, or the lens page URL as fallback
  - `product_name` (str) — e.g. `Viltrox TC-2.0X FE`
  - `product_model` (str) — the matched lens display name
  - `product_type` (str) — `"Lens"`
- Parse strategy: index page (BeautifulSoup) → find the lens link whose label matches the requested model display name (or matches the page slug fallback) → follow the `/pages/<slug>` link → isolate the `### Document Download` section → first `<lens name> V<version>` line is the latest.
- Error codes: `network_error`, `parse_error`, `product_not_found`, `firmware_not_available`, `download_url_not_found`.
- Fixture tests: at minimum one captured index page fixture and one captured lens page fixture; pytest cases verify both happy path and rejection of companion app version strings.
- `mypy --strict` clean; Ruff clean; follows the same `asyncio.new_event_loop` pattern as the existing official modules for parity.

## Assumptions & Risks
- **Assumption**: Viltrox continues to host `https://viltrox.com/pages/download-center-1` and per-lens `/pages/<slug>` pages in the observed structure. The index lists the lenses in a side menu and the per-lens pages contain a `### Document Download` section.
- **Assumption**: The lens display name on the index (e.g. `TC-2.0X FE`) maps to a `product_model` that operators can configure. The page slug serves as a fallback when the display name does not match an entry directly.
- **Assumption**: The companion app section is clearly distinguishable from per-lens firmware sections; the module restricts parsing to the `### Document Download` section on a per-lens page and never treats an app-version string as a lens firmware version.
- **Risk**: Viltrox page structure changes (e.g. section renamed, sidebar replaced by a JavaScript widget, model names localized) — mitigated by per-invocation error boundary (E007) and `parse_error` surfacing, plus the official module health monitor (E020) for repeated failures.
- **Risk**: The `V<version>` format is not consistent across all entries (e.g. some lenses may not use a leading `V`) — mitigated by fixture-based coverage and a version-normalization step that tolerates both `V1.03` and `1.03` forms.
- **Risk**: Many lenses on the index may not have an active firmware download section (legacy or hardware revisions without firmware updates) — the module must report `firmware_not_available` rather than guess.
- **Risk**: Responsible-scraping posture (Project Instructions §II) is mandatory — the module must use the host-provided ScrapeClient and avoid high-frequency polling; the per-module default check interval applies.

## Glossary
- **Viltrox Lenses module**: The new official `viltrox_lenses` module shipped under `backend/src/binocular/official_modules/`. Its `SUPPORTED_DEVICE_TYPE` is `lens` and its model key is the lens display name (e.g. `TC-2.0X FE`).
- **Index page**: `https://viltrox.com/pages/download-center-1` — the Viltrox download-center landing page that lists ~70 lenses across 6 mount groups (FE / E / X / Z / M / DL) with each lens linked to its own `/pages/<slug>` page.
- **Lens page**: A per-lens `/pages/<slug>` page that contains a `### Document Download` section listing firmware releases.
- **Document Download section**: A `### Document Download` Markdown section on a lens page whose entries follow the pattern `<lens name> V<version>` (e.g. `TC-2.0X FE V1.03`). The first entry is treated as the latest.
- **Top entry**: The first firmware entry inside the `### Document Download` section, used as the latest version.
- **Lens display name**: The human-readable lens identifier as it appears on the index (e.g. `TC-2.0X FE`). Used as the primary `model` value when configuring a Viltrox device.
- **Page slug**: The URL slug portion of a per-lens page URL (e.g. `tc-2-0x-fe`). Used as a fallback when the lens display name does not match an index entry directly.
- **Companion app version**: The `Viltrox Lens V1.13 for Mac/Win` desktop application version, which is not a lens firmware version and must be excluded from parsing.
- **Two-step flow**: The required navigation pattern — first fetch the index, then follow the per-lens link — implemented via the host-provided polite ScrapeClient.
- **Authoring contract**: The strict, documented interface (per ADR-0005) every module must implement: `check_firmware(url, model, http_client) -> dict`, plus `MODULE_VERSION` and `SUPPORTED_DEVICE_TYPE` constants.
