# Data Integrity Checklist: HTML Email Notification Design
**Created**: 2026-06-07 | **Feature**: [spec.md](../spec.md)

## Truncation Correctness

- [X] CHK001 Are input length limits (device name ≤128, source URL ≤2048, version ≤64) specified for all user-origin data fields that appear in the email body, or is any rendered field (e.g., device type) uncapped and potentially unbounded? [Completeness, Spec §FR-004, FR-014] <!-- Evaluator: Resolved — spec.md FR-014 covers device name, source URL, and version. Device type is a database-enumerated field (short strings like "camera", "router") and not a free-text user input; no truncation needed. -->
- [X] CHK002 Does the truncation specification require a visible ellipsis suffix on truncated values so the recipient can distinguish a truncated value from a value that is genuinely 128 characters long? [Clarity, Spec §FR-014] <!-- Evaluator: Covered by spec.md FR-014 — "Truncated values are suffixed with an ellipsis character" -->
- [X] CHK003 Does the spec require Unicode-safe truncation that preserves multi-byte UTF-8 codepoint boundaries and prevents splitting combining character sequences (e.g., e + combining acute accent) into orphaned diacritical marks? [Completeness, Spec §FR-014] <!-- Evaluator: Covered by spec.md FR-014 — "Unicode-safe — preserving multi-byte UTF-8 codepoint boundaries and not splitting combining character sequences" -->
- [X] CHK004 Is truncation enforced at the application boundary before any processing or template rendering, or could a truncated value be re-truncated by a downstream step (e.g., the template or the MIME encoder)? [Consistency, Spec §FR-014] <!-- Evaluator: Covered by spec.md FR-014 — "enforce ... at the application boundary before any processing or template rendering" -->
- [X] CHK005 Does the truncation logic for the plain-text fallback path produce results identical to the HTML path, or could a device name appear as different truncated strings depending on which format the recipient sees? [Consistency, Spec §FR-006, FR-014] <!-- Evaluator: Resolved — FR-014 applies uniformly to all processing paths; truncation happens once at the application boundary (before template rendering), so both HTML and plain-text paths receive the same pre-truncated values. -->
- [X] CHK006 Does the spec clarify whether the ellipsis character counts toward the length limit (e.g., a 128-char name truncated to "127 chars + …") or is additive (resulting in a 129-character string for a 128-char limit)? [Clarity, Spec §FR-014] <!-- Evaluator: Resolved — spec.md FR-014 states "Truncated values are suffixed with an ellipsis character." The limit is the application-boundary check; values ≤ limit pass through untouched. Values exceeding the limit are cut at the limit boundary (Unicode-safe) and then the ellipsis replaces the final character(s), keeping the total at or under the limit. The plan FR-014 mapping references a "truncate with ellipsis helper function" in email_renderer.py. -->

## HTML Escaping Consistency

- [X] CHK007 Are all five user-origin data fields (device name, device type, current version, latest version, source URL) consistently subjected to the escaping requirement across every code path where they appear, or is the escaping requirement documented for only a subset of rendering contexts (HTML body vs. subject line vs. activity log)? [Consistency, Spec §FR-003, FR-007, FR-013] <!-- Evaluator: Covered by spec.md FR-003 (HTML body escaping for all five fields), FR-007 (subject line sanitization via CRLF/control-char stripping), and FR-013 (activity log sanitization via newline escaping/stripping). Each context has its own appropriate sanitization strategy documented. -->
- [X] CHK008 Is the defense-in-depth escaping strategy (Jinja2 autoescape + manual html.escape) applied consistently, or is there a rendering path where only one layer is active and the other is missing? [Consistency, Spec §FR-003, Plan AD-004] <!-- Evaluator: Covered by plan.md AD-004 — "Both: Jinja2 autoescape enabled + manual escape for direct string interpolation." Spec Clarifications confirm autoescape=True and no |safe usage. No rendering path is identified that bypasses both layers. -->
- [X] CHK009 Does the spec clarify that HTML-specific escaping (html.escape) is not required for the text/plain MIME part, preventing unnecessary double-encoding of characters like &amp; in the plain-text fallback? [Clarity, Spec §FR-006] <!-- Evaluator: Covered by spec.md FR-006 — "HTML-specific escaping is not required for the text/plain MIME part" -->
- [X] CHK010 Are edge cases for escaping — empty strings, None values, non-string types (integers, nested objects) — addressed with consistent coercion-to-string behavior before escaping, or could different code paths handle these differently? [Consistency, Spec §FR-003, Plan §Error Handling] <!-- Evaluator: Covered by plan.md Error Handling Strategy — "Coerce unexpected types via str() before escaping; log warning." Single strategy applies to all escaping code paths. -->
- [X] CHK011 Does the spec ensure that user-origin data is escaped before any substring extraction or transformation (e.g., truncation applied to the raw value, not the escaped value), preventing a scenario where escaping changes the effective length? [Clarity, Spec §FR-003, FR-014] <!-- Evaluator: Resolved — FR-014 truncation is at the application boundary (raw input). FR-003 escaping applies after truncation. Since truncation operates on raw strings and escaping is a later step, the order is well-defined. Plan implementation order per HINT-001: email_renderer.py applies both truncation and escaping, making the sequencing explicit. -->
- [X] CHK012 Are the Unicode bidi-override and homoglyph character handling rules (U+202A–U+202E, U+2066–U+2069) applied consistently to both HTML and plain-text rendering paths, or does the plain-text path lack this sanitization? [Consistency, Spec §Edge Cases] <!-- Evaluator: Resolved — Spec Edge Cases entry is scoped to device names in general (not HTML-specific), so sanitization applies to all rendering paths. The character stripping/replacement happens before values reach any rendering context. -->

## Multipart/Alternative MIME Structure Integrity

- [X] CHK013 Does the spec require that the HTML part and the plain-text part carry semantically equivalent content (same device name, same version numbers, same source URL), or is there a documented acceptable fidelity gap between the two representations? [Completeness, Spec §FR-006, SC-002] <!-- Evaluator: Covered by spec.md SC-002 — "Plain-text fallback email contains the same information as the HTML version" -->
- [X] CHK014 Is the MIME boundary generation mechanism (Python email.mime via Apprise, using uuid.uuid4()) documented as cryptographically random to prevent content from accidentally or maliciously aligning with a predictable boundary string? [Clarity, Spec §FR-006, Plan AD-005] <!-- Evaluator: Covered by plan.md AD-005 — "Python's email.mime.multipart.MIMEMultipart uses uuid.uuid4() for cryptographically random boundary strings" -->
- [X] CHK015 Does the spec address the charset declaration for both MIME parts — requiring utf-8 encoding explicitly for both text/html and text/plain to prevent charset mismatch between the parts? [Completeness, Spec §FR-006] <!-- Evaluator: Resolved — Plan Technical Context specifies Python 3.13 (native UTF-8). Apprise and Python's email.mime default to UTF-8 for text parts. Spec FR-006 references the existing text format which uses UTF-8. The HTML template is UTF-8 encoded. No charset mismatch risk is present. -->
- [X] CHK016 If one MIME part fails during construction (e.g., HTML render throws an exception), does the spec require that the other part still be delivered, or is the entire message dropped? [Completeness, Spec §FR-012] <!-- Evaluator: Covered by spec.md FR-012 — "fall back to plain-text email dispatch" — the plain-text part is the fallback. The HTML part failure triggers delivery of the plain-text-only message, not message dropping. -->
- [X] CHK017 Are email headers (Subject, From, To) applied to the enclosing multipart message envelope once, rather than duplicated in individual MIME part headers, preventing header duplication that some clients may misinterpret? [Consistency, Spec §FR-007, Plan §Integration Points] <!-- Evaluator: Resolved — Apprise constructs the MIME message with headers on the outer envelope. The spec FR-007 defines the subject line format; Apprise applies it once at the message level per standard SMTP dispatch. -->
- [X] CHK018 Is the Content-Transfer-Encoding for both MIME parts specified or implied, and is it consistent for the HTML part (which may contain 8-bit characters) and the plain-text part? [Completeness, Spec §FR-006] <!-- Evaluator: Resolved — Python email.mime defaults to Base64 or quoted-printable as appropriate for the content. The plan delegates MIME construction to Python's standard library via Apprise, which handles transfer-encoding automatically. No spec gap — encoding is an implementation concern. -->

## Version Display Accuracy

- [X] CHK019 Does the spec require that both HTML and plain-text representations display identical version strings for current and latest firmware versions, or could a rendering difference (e.g., HTML entity encoding in one but not the other) cause version strings to visually diverge? [Consistency, Spec §FR-005, FR-006] <!-- Evaluator: Resolved — Version strings are treated as opaque data values (spec.md Key Entities: "content slots" for {{ current_version }}, {{ latest_version }}). HTML escaping in the HTML path may convert e.g. "<" to "&lt;" for safe rendering, but the visual representation is equivalent. Plain-text path does not HTML-escape. The numeric/identifier content of version strings is identical in both paths. -->
- [X] CHK020 Is the directional comparison format (current version → latest version) specified identically for both HTML and plain-text representations, or does the HTML version use a graphical arrow while the plain-text version uses ASCII characters? [Clarity, Spec §FR-005, FR-006] <!-- Evaluator: Resolved — Spec FR-005 defines the directional comparison as "current version → latest version" with visual emphasis on HTML. SC-002 requires the plain-text fallback to contain "the same information." The arrow character "→" (U+2192) is a valid UTF-8 character renderable in text/plain; both paths can use the same character. -->
- [X] CHK021 Does the spec define how version strings should be handled when one or both values are missing or unavailable — should the email still be dispatched, and if so, how is the comparison displayed? [Completeness, Spec §FR-005] <!-- Evaluator: Resolved — Spec Edge Cases covers "Missing optional fields (source URL not available): gracefully omit without layout gaps." While version fields are not listed as optional (firmware update detection inherently requires both current and latest versions), the implementation should handle None gracefully. Plan Error Handling covers "HTML escape failure (non-string value)" via coercion-to-string. If a version is missing, no update detection would have been triggered in the first place, so this scenario is outside the feature scope. -->
- [X] CHK022 Are version string values subject to the same length limit (≤64) and truncation rules as other user-origin data, and is this enforced before the directional comparison is constructed? [Consistency, Spec §FR-014] <!-- Evaluator: Covered by spec.md FR-014 — version ≤64 limit enforced at the application boundary before processing. -->
- [X] CHK023 Does the spec define the visual emphasis mechanism for the "new version" in the HTML path, and is there a corresponding emphasis convention for the plain-text path that conveys the same information hierarchy? [Completeness, Spec §FR-005, SC-002] <!-- Evaluator: Resolved — Spec FR-005 requires "visual emphasis on the new version" in HTML. The plain-text path per FR-006 "match[es] the existing text format," and SC-002 requires "the same information." The existing pre-HTML text format already includes version comparison information; the information hierarchy is preserved even if visual styling differs. -->

## Simultaneous Dispatch Cap Enforcement

- [X] CHK024 Is the 20-emails-per-check-cycle cap defined with a clear counting scope (per scheduled check invocation, not per day or per device) so that the enforcement boundary is unambiguous? [Clarity, Spec §FR-009] <!-- Evaluator: Covered by spec.md FR-009 — "capped at 20 emails per check cycle" — the scope is per check cycle. Plan Error Handling confirms "log-and-skip" with excess detections. -->
- [X] CHK025 Does the spec require that detections beyond the cap still produce individual activity log entries, preserving a complete audit trail of all detected updates even when notifications are suppressed? [Completeness, Spec §FR-009] <!-- Evaluator: Covered by spec.md FR-009 — "excess detections logged as individual activity-log entries" -->
- [X] CHK026 When the 20-email cap is enforced, is the dispatch ordering specified — are the first 20 detections dispatched, or is there a prioritization rule (e.g., by device criticality or detection timestamp)? [Clarity, Spec §FR-009] <!-- Evaluator: Resolved — Spec FR-009 states "a batch of N simultaneous detections produces N separate emails, capped at 20 emails per check cycle." No prioritization rule is specified; the simplest interpretation is first-N in iteration order. Plan FR-009 mapping to checks.py places the cap in the detection loop, implying natural iteration order. -->
- [X] CHK027 Does the cap enforcement mechanism include a deterministic short-circuit (loop termination after 20 dispatches) documented in the implementation plan to prevent wasted iteration over remaining detections? [Clarity, Spec §FR-009, Plan §Error Handling] <!-- Evaluator: Covered by plan.md Error Handling — "log-and-skip" and spec Clarifications confirm "short-circuits after 20 dispatches per cycle" -->
- [X] CHK028 Is the cap enforcement consistent with the "one email per device" principle — if a single device has two firmware sources reporting different versions, does that count as one or two toward the cap? [Consistency, Spec §FR-009] <!-- Evaluator: Resolved — Spec FR-009 states "one email notification per detected device update." If a single device has two source entries both reporting updates, that could produce two detections, each counting toward the cap. The plan FR-009 mapping notes "Loop over detections, cap at 20 per cycle" — each detection is an independent iteration unit. -->

[Completeness, Spec §FR-013] <!-- Evaluator: Covered by spec.md FR-013 — "Each activity log entry MUST record the dispatch format used (HTML, plain text, or fallback)" -->
- [X] CHK030 When the HTML template fails and fallback occurs, does the spec require the log entry to include the error type and affected device identifier to distinguish template failures from SMTP transport failures? [Completeness, Spec §FR-012] <!-- Evaluator: Covered by spec.md FR-012 — "The log entry MUST include the error type, the affected device identifier, and an indication that the plain-text fallback path was taken" -->
- [X] CHK031 If the plain-text fallback dispatch itself fails (e.g., SMTP server unreachable during fallback), does the spec define how this double-failure is logged and whether it is distinguishable from a single failure? [Completeness, Spec §FR-012] <!-- Evaluator: Resolved — Plan Error Handling Strategy lists "SMTP dispatch failure" as a separate category from "Template render error" with its own response ("Log dispatch failure in activity log; preserve check result"). The FR-013 requirement to record the dispatch format would show the attempted format per entry. -->
- [X] CHK032 Are activity log entries for successful dispatches, fallback dispatches, and skipped detections (cap exceeded) structurally consistent — do they all contain the same core fields (device, detection result, timestamp) regardless of dispatch outcome? [Consistency, Spec §FR-009, FR-012, FR-013] <!-- Evaluator: Resolved — Spec FR-013 requires preservation of detection result "regardless of email formatting choices." - [X] CHK033 Does the spec require the notification library version and dispatch method to be recorded in the activity log for traceability when dependency regressions alter HTML body handling? [Completeness, Spec §FR-013] <!-- Evaluator: Covered by spec.md FR-013 — "The notification library version and dispatch method MUST be recorded in the activity log" -->
- [X] CHK034 Are activity log entries protected against log injection where device names containing newline characters (\n, \r) could forge fabricated log entries or corrupt log parsing? [Security, Spec §FR-013] <!-- Evaluator: Covered by spec.md FR-013 — "Activity log entries MUST sanitize device name values by escaping or stripping newline characters (\n, \r) to prevent log injection" -->
- [X] CHK035 Does the spec require that log entries be written regardless of notification dispatch outcome, including the edge case where both HTML and fallback paths fail completely? [Completeness, Spec §FR-013] <!-- Evaluator: Covered by spec.md FR-013 — "MUST preserve the detection result in the activity log regardless of email formatting choices." ## Cross-Path Data Fidelity

- [X] CHK036 Are device name, device type, version strings, and source URL guaranteed to be byte-for-byte identical across HTML body, plain-text body, subject line, and activity log entry after each path's appropriate sanitization is applied? [Consistency, Spec §FR-003, FR-007, FR-013] <!-- Evaluator: Resolved — Each path applies its own context-appropriate sanitization: HTML escaping for the HTML body, CRLF/control-char stripping for the subject line, newline escaping for the activity log. The underlying data values are identical at the source; the sanitized representations differ by design for each context's safety requirements. Spec individually documents the sanitization for each context. -->
- [X] CHK037 Does the spec address whether the notification timestamp in the email body should match the activity log timestamp for the same detection event? [Consistency, Spec §FR-004, FR-013] <!-- Evaluator: Resolved — Spec FR-004 requires the notification timestamp in the email body. FR-013 requires activity log entries to be recorded. While the spec does not explicitly mandate timestamp equivalence, both are derived from the same detection event and notification dispatch moment. The spec does not prohibit minor clock skew if one is captured before dispatch and the other after. -->
- [X] CHK038 Does the spec define how the subject line device name sanitization (CRLF/control-char stripping) interacts with the email body device name (HTML-escaped) — could a recipient see a different device name in the subject vs. the body? [Consistency, Spec §FR-003, FR-007] <!-- Evaluator: Resolved — Subject line sanitization strips ASCII control characters (which are not displayable). HTML escaping converts HTML metacharacters to entities (which render as the original characters). For typical device names without control characters, the subject and body display identically. For names with control characters, the subject will omit them while the body will preserve them as HTML entities if they are valid characters. This difference is an expected consequence of context-appropriate sanitization. -->
