# Security Checklist: HTML Email Notification Design
**Created**: 2026-06-07 | **Feature**: [spec.md](../spec.md)

## HTML Escaping & Sanitization

- [X] CHK001 Are all user-origin data fields (device names, version strings, source URLs) explicitly enumerated in the escaping requirement, or is there ambiguity about which fields must be escaped? [Completeness, Spec §FR-003] <!-- Evaluator: Covered by spec.md FR-003 — all five fields (device name, device type, current version, latest version, source URL) now explicitly enumerated -->
- [X] CHK002 Does the design require both Jinja2 autoescape and manual `html.escape()` as defense-in-depth, and is the order of application (escape before rendering) unambiguously specified? [Consistency, Spec §FR-003, Plan AD-004] <!-- Evaluator: Covered by plan.md AD-004 (both) and spec.md Clarifications ("before template insertion") -->
- [X] CHK003 Are all five HTML-significant metacharacters (`<`, `>`, `&`, `"`, `'`) covered by the escaping requirement, or are quote characters omitted? [Clarity, Spec §FR-003] <!-- Evaluator: Resolved — added `'` to Edge Cases metacharacters list and specified `html.escape(s, quote=True)` -->
- [X] CHK004 Is the escaping applied before Jinja2 variable substitution rather than after, preventing a time-of-check/time-of-use gap where unescaped data could reach the renderer? [Clarity, Spec §Clarifications] <!-- Evaluator: Covered by spec.md Clarifications — "Apply html.escape() ... before template insertion" -->
- [X] CHK005 Are non-string input types (integers, None, nested objects) that could bypass `html.escape()` addressed with a coercion-to-string strategy before escaping? [Completeness, Spec §FR-003, Plan §Error Handling] <!-- Evaluator: Covered by plan.md Error Handling Strategy — "Coerce unexpected types via str() before escaping; log warning" -->
- [X] CHK006 Does the plain-text multipart/alternative fallback body also escape or sanitize user-origin data for safe `text/plain` MIME rendering, or is escaping assumed unnecessary for text content? [Completeness, Spec §FR-006] <!-- Evaluator: Resolved — added note to FR-006 that text/plain does not interpret HTML metacharacters and HTML-specific escaping is not required -->

## Template Injection Prevention

- [X] CHK007 Is Jinja2 autoescape enabled for all template rendering contexts without any opt-out paths or per-variable `|safe` filter overrides that could bypass escaping? [Completeness, Spec §FR-003, Plan AD-004] <!-- Evaluator: Covered by plan.md HINT-002 (autoescape=True), spec Clarifications (no |safe usage in template) -->
- [X] CHK008 Are all user-supplied values passed exclusively as Jinja2 template variables (dictionary context), with no code path that concatenates user data into the raw template string before parsing? [Security, Spec §FR-003, Plan AD-004] <!-- Evaluator: Covered by spec.md Key Entities (named placeholders) and Clarifications (no raw template concatenation) -->
- [X] CHK009 Does any error-handling or fallback code path construct HTML strings via manual concatenation that could reintroduce injection if the template renderer fails? [Completeness, Spec §FR-003, Plan AD-004] <!-- Evaluator: Covered by plan.md Error Handling — fallback is plain-text only, no HTML construction in error path -->
- [X] CHK010 Are color tokens and other non-user template parameters (e.g., `{{ accent_color }}`) sourced exclusively from hardcoded constants or a trusted configuration source, never from user input? [Security, Spec §FR-010] <!-- Evaluator: Covered by spec.md FR-010 (hardcoded hex values) and plan FR-010 mapping ("hardcoded as hex values in template") -->
- [X] CHK011 Does the HTML template file contain only markup, placeholder variables, and standard Jinja2 control-flow constructs — with no custom filters, extensions, or executable Python code blocks? [Security, Spec §FR-001, Plan AD-001] <!-- Evaluator: Covered by spec.md Key Entities (named placeholders + control flow only) and plan AD-001 ("clean separation of markup and logic") -->

## Email Content & MIME Security

- [X] CHK012 Are MIME multipart/alternative boundary strings generated using a cryptographically random source to prevent an attacker from injecting content that aligns with a predictable boundary? [Security, Spec §FR-006] <!-- Evaluator: Resolved — added plan AD-005 documenting that Python's email.mime via Apprise uses uuid.uuid4() for cryptographically random boundaries -->
- [X] CHK013 Are email headers (Subject line, From address) protected against header injection if device names contain CRLF sequences (`\r\n`) that could terminate the header and inject additional headers? [Security, Spec §FR-007] <!-- Evaluator: Resolved — updated FR-007 to require stripping of CRLF sequences, null bytes, and ASCII control characters from device names before header insertion -->
- [X] CHK014 Does the subject line construction handle device names containing null bytes or other control characters that could cause header truncation or MIME parser confusion? [Robustness, Spec §FR-007] <!-- Evaluator: Resolved — updated FR-007 to require stripping of null bytes and ASCII control characters (0x00–0x1F, 0x7F) from device names before header insertion -->
- [X] CHK015 Is the source URL validated as a well-formed URL restricted to `http` and `https` schemes before inclusion in the email body, preventing `javascript:` or `data:` URI injection? [Security, Spec §FR-004] <!-- Evaluator: Resolved — updated FR-003 to require source URL validation as well-formed http/https scheme URLs before inclusion -->
- [X] CHK016 Does the HTML email avoid all external resource references (remote images, web fonts, external stylesheets) that could function as tracking beacons or expose the recipient's reading behavior? [Security, Spec §FR-002] <!-- Evaluator: Covered by spec.md FR-002 (inline CSS only), scope Excludes — no external resources referenced -->
- [X] CHK017 Are all inline CSS `style` attribute values constructed exclusively from trusted constant strings, preventing a user-supplied field from injecting arbitrary CSS properties or `url()` expressions? [Security, Spec §FR-002] <!-- Evaluator: Covered by spec.md FR-002 (inline CSS from template, not user data) and FR-010 (hardcoded color constants) -->
- [X] CHK018 Does the truncation logic for device names, URLs, and version strings safely handle multi-byte UTF-8 characters (e.g., emoji, combining characters) without splitting mid-codepoint or producing invalid byte sequences? [Robustness, Spec §FR-014] <!-- Evaluator: Resolved — updated FR-014 to require Unicode-safe truncation preserving multi-byte UTF-8 codepoint boundaries and combining character sequences -->
- [X] CHK019 Do the `word-break` and `overflow-wrap` CSS rules prevent a maliciously long unbroken string from forcing critical version-delta information outside the visible card area on narrow viewports? [Security, Spec §FR-015] <!-- Evaluator: Covered by spec.md FR-015 and plan FR-015 mapping (CSS word-break: break-word; overflow-wrap: break-word) -->

- [X] CHK021 Are SMTP credentials and full connection strings explicitly excluded from all log output — activity log entries, error messages, debug traces, and stack traces — with a redaction or sanitization mechanism in place? [Security, Spec §FR-013] <!-- Evaluator: Resolved — updated FR-013 to require redaction of SMTP credentials and Apprise connection URLs from all log output; plan Security section documents redaction -->
- [X] CHK022 Does the SMTP connection require TLS or STARTTLS for all credential transmission, with no plaintext authentication fallback permitted? [Security, Plan §Integration Points] <!-- Evaluator: Resolved — plan.md Security section now documents Apprise SMTP configured for TLS/STARTTLS with no plaintext auth fallback -->
- [X] CHK023 Are SMTP credentials injected via environment variables or container secrets rather than baked into the Docker image or committed to source control? [Security, Plan §Technical Context] <!-- Evaluator: Resolved — plan.md Security section documents SMTP credentials sourced from environment variables, not stored in source or Docker images -->
- [X] CHK024 Are Apprise SMTP connection URLs (which may embed credentials) sanitized or redacted before appearing in any log message, warning, or exception trace? [Security, Plan §Error Handling] <!-- Evaluator: Resolved — updated FR-013 to require redaction of Apprise connection URLs from all log output; plan Security section documents URL redaction -->

## Activity Log Integrity

- [X] CHK025 Does the specification require that both successful and failed dispatch attempts produce durable, timestamped activity log entries, or is there a gap where silent failures could go unrecorded? [Completeness, Spec §FR-013] <!-- Evaluator: Covered by spec.md FR-013 ("preserve the detection result... regardless of email formatting") and plan Error Handling (both template and SMTP failures logged) -->
- [X] CHK026 Are template construction failures logged with sufficient distinguishing context (error type, affected device, fallback path taken) to differentiate them from SMTP transport failures during incident investigation? [Completeness, Spec §FR-012] <!-- Evaluator: Resolved — updated FR-012 to require log entry include error type, affected device identifier, and indication that the plain-text fallback path was taken -->
- [X] CHK027 Are detection events that exceed the 20-email-per-cycle cap logged with a distinct, auditable status to preserve a complete detection audit trail even when notifications are suppressed? [Completeness, Spec §FR-009] <!-- Evaluator: Covered by spec.md FR-009 ("excess detections logged as individual activity-log entries") and plan Error Handling ("Log excess detections as activity-log entries with 'skipped' status") -->
- [X] CHK028 Does each activity log entry record the dispatch format used (HTML, plain text, or fallback) to enable post-incident determination of which format path was active for a given notification? [Completeness, Spec §FR-011] <!-- Evaluator: Resolved — updated FR-013 to require each activity log entry record the dispatch format used (HTML, plain text, or fallback) -->
- [X] CHK029 Are activity log entries protected against log injection where device names containing newline characters (`\n`, `\r`) could forge fabricated log entries or corrupt log parsing? [Security, Spec §FR-013] <!-- Evaluator: Resolved — updated FR-013 to require sanitization of device name values by escaping or stripping newline characters in activity log entries -->
- [X] CHK030 Does the activity log capture the notification library version or dispatch method for traceability when dependency regressions alter HTML body handling? [Observability, Spec §Risks] <!-- Evaluator: Resolved — updated FR-013 to require notification library version and dispatch method be recorded in the activity log -->

## Channel Confusion & Dispatch Integrity

- [X] CHK031 Is the per-channel dispatch logic structured so that Gotify cannot receive HTML-formatted content under any code path — including error fallback, configuration reload, or concurrent dispatch scenarios? [Security, Spec §FR-008] <!-- Evaluator: Covered by spec.md FR-008, plan HINT-005 (per-channel dispatch with protocol inspection), and plan Risk Mitigation (explicit per-channel format check; Gotify always body_format=None) -->
- [X] CHK032 Does the channel protocol detection handle edge cases where a misconfigured channel URL type (e.g., a Gotify URL mistakenly stored in an SMTP configuration field) could route HTML content to a text-only channel? [Robustness, Spec §FR-008] <!-- Evaluator: Resolved — Apprise determines protocol from URL scheme (smtp:// vs gotify://); plan HINT-005 documents per-channel protocol inspection making URL misconfiguration self-correcting -->
- [X] CHK033 Are test notifications unconditionally dispatched as plain text even when the target channel is SMTP configured with HTML capability, preventing test-path HTML leakage? [Consistency, Spec §FR-011] <!-- Evaluator: Covered by spec.md FR-011 ("test notifications always use plain text regardless of channel type") and plan FR-011 mapping -->
- [X] CHK034 Does the 20-email-per-cycle cap include a mechanism (e.g., short-circuit counting, early termination of the detection loop) to prevent resource exhaustion from a flood of firmware detections across many devices? [Security, Spec §FR-009] <!-- Evaluator: Covered by spec.md FR-009 (cap at 20 per cycle) and plan Error Handling (log-and-skip; excess detections logged with "skipped" status); spec Clarifications now confirms short-circuit loop termination -->

## Error Handling & Fail-Safe

[Security, Plan §Performance Goals] <!-- Evaluator: Resolved — plan.md Security section documents a 5-second timeout enforced via asyncio.wait_for on Jinja2 template rendering -->
- [X] CHK036 Does the fallback-to-plain-text mechanism guarantee that no notification is silently dropped when HTML template rendering fails, and is this guarantee testable under induced failure conditions? [Reliability, Spec §FR-012] <!-- Evaluator: Covered by spec.md FR-012 (fallback to plain-text and log error) and plan Testing Strategy Security tier ("template error path tested with induced failure conditions") -->
- [X] CHK037 Are input length validations (device name ≤128, URL ≤2048, version ≤64) enforced at the application boundary before any processing or template rendering, preventing memory exhaustion from unbounded input? [Security, Spec §FR-014] <!-- Evaluator: Resolved — updated FR-014 to require input length limits enforced at the application boundary before any processing or rendering -->
- [X] CHK038 Are all third-party dependencies (Jinja2, Apprise) pinned to specific versions and vetted against known security advisories, with a process defined for reviewing advisories on dependency upgrades? [Security, Plan §Primary Dependencies] <!-- Evaluator: Resolved — plan.md Primary Dependencies updated to pin Apprise v1.11.0 and Jinja2 v3.1.x; Dependabot/safety advisory review documented -->
- [X] CHK039 Does the escaping requirement cover all five data fields inserted into the email body (device name, device type, current version, latest version, source URL), or is there a subset that could be missed? [Completeness, Spec §FR-004] <!-- Evaluator: Resolved — updated FR-003 to explicitly enumerate all five fields: device name, device type, current version string, latest version string, source URL -->
- [X] CHK040 Does the escaping strategy account for Unicode bidi-override and homoglyph characters in device names that could visually reorder or spoof trusted email content when rendered by the email client? [Security, Spec §Edge Cases] <!-- Evaluator: Resolved — added Unicode bidi-override and homoglyph character handling to spec.md Edge Cases (strip/replace U+202A–U+202E, U+2066–U+2069) -->
