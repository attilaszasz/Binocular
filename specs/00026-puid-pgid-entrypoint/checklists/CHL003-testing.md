# Testing Requirements Quality Checklist: PUID/PGID Entrypoint

**Domain**: Testing | **Depth**: Standard | **Audience**: Reviewer
**Focus Areas**: Verification Criteria Testability, Test Coverage Scope, Edge Case Coverage, Acceptance Criteria Completeness

---

## Verification Criteria Testability

- [ ] CHK001 Are all verification criteria expressed as deterministic, scriptable assertions (Given/When/Then) with unambiguous expected values, or do any rely on human judgment or post-hoc inspection? [Testability, §Spec §Verification Criteria] <!-- Evaluator: VC-1 through VC-5 use the Given/When/Then pattern, but VC-1's "owns /app/data and /app/modules" is ambiguous without specifying which file attributes to check (owner UID/GID on each path recursively vs. top-level only) and whether verification uses `docker exec id` + `stat`, `ls -la`, or a different mechanism. The phrase "owns" conflates user ownership with group ownership and does not specify whether subdirectories or file contents are sampled. -->

- [ ] CHK002 Does VC-1 independently assert both UID and GID (per STF-003 resolution) with the expected username `app` via a specific verification command, or is GID verification still implicitly bundled with UID assertion? [Precision, §STF-003, §VC-1] <!-- Evaluator: STF-003 resolved that VC-1 should assert UID, GID, and username. The current spec text includes "username app" but does not specify how the username is verified (e.g., `id -nu 1001` yields "app" vs `getent passwd 1001` yields "app:x:..."). Different assertion strategies could yield different results if there are multiple users sharing the same UID or if the user entry's name field is unexpectedly truncated. The spec also does not require verifying the GID via `id -ng` or equivalent. -->

- [ ] CHK003 Is there a verification criterion for the independent-default behavior (one var set, the other absent), or is this common operational scenario covered only by edge-case documentation? [Coverage, §OR-002, §Edge Cases] <!-- Evaluator: OR-002 defines independent defaults and the Edge Cases document "PUID=1500 with absent PGID → UID 1500, GID 1000", but no VC tests this scenario. This is the second most common operational use case (after the all-default case) and is explicitly called out in both OR-002 and the edge cases as a required behavior. Without a VC, the independent-default contract is not acceptance-tested. -->

- [ ] CHK004 Are VC outcomes tied to specific observable outputs (exit codes, log line content, file ownership attributes) that can be programmatically asserted in CI, or are they expressed at a level that requires manual operator verification? [Automation Feasibility, §VC 1-5, §OR-003, §OR-006] <!-- Evaluator: VC-3 says "container exits with an error" but does not specify the exit code or the expected error message string. An automated test suite cannot distinguish between root-refusal exit (expected) and a crash from a different cause (unexpected) without a documented exit code contract or error message pattern. Similarly, VC-5 says "a warning is logged" but does not specify the expected warning text pattern, log sink, or how to programmatically capture it. -->

- [ ] CHK005 Does VC-5 test both PUID and PGID non-numeric simultaneously but omit the asymmetric case where one is numeric and the other is non-numeric, missing the most likely operator error? [Coverage, §VC-5, §OR-006] <!-- Evaluator: VC-5 tests both PUID=abc and PGID=def together (both invalid). The more realistic scenario — a typo on one variable while the other is correct (e.g., PUID=1001, PGID=abc) — is not tested. This asymmetric case triggers the independent-default logic AND the warning-only path simultaneously, creating a different operational state than the all-invalid case tested by VC-5. -->

## Test Coverage Scope

- [ ] CHK006 Does the test strategy cover all six operational requirements (OR-001 through OR-006) with at least one verification criterion or explicit test case per requirement? [Coverage, §Spec §Operational Requirements] <!-- Evaluator: OR-001 (read env vars) is implicitly tested across VCs 1-5 but never explicitly verified with a test that sets then reads back the env var. OR-002 (independent defaults) is untested per CHK003. OR-005 (exec su-exec) has no dedicated VC — no test confirms that `exec` is used or that signals propagate correctly to uvicorn. The plan's Testing Strategy does not reference OR-005 at all. An implementer could fulfill all VCs without satisfying OR-005. -->

- [ ] CHK007 Is the su-exec-to-gosu fallback (AD-001) tested in at least one CI scenario, or does the test strategy assume su-exec is always available, leaving the gosu path untested? [Coverage, §AD-001, §Plan §Risk Mitigation] <!-- Evaluator: The plan documents gosu as a fallback for arm64 and lists it in Risk Mitigation, but the testing strategy only covers "docker build + docker inspect" and "docker run + id". There is no test scenario where su-exec is deliberately absent to verify the gosu fallback path, the fallback error message, and equivalent behavior. If gosu handles groups, capabilities, or signal forwarding differently (per the spec's own operational constraint about verifying equivalence), this difference would go undetected. -->

- [ ] CHK008 Are the chown failure modes (hard error on data volumes, warning on read-only rootfs, symlink behavior with --no-dereference) tested, or does the test strategy only cover the success path? [Coverage, §OR-004, §Operational Constraints] <!-- Evaluator: The operational constraints specify different failure handling per volume type and mandate --no-dereference for symlinks. The test strategy (plan) mentions only "Container runs with configured PUID/PGID; volumes owned by correct user." No test validates chown failure behavior on read-only rootfs (warning + continue), chown failure on data volumes (hard error + exit), or symlink dereference protection. These are distinct operational paths with different failure semantics that are not verified. -->

- [ ] CHK009 Are both the PUID=0 and PGID=0 refusal cases independently tested as separate test cases with distinct expected error messages, or could a test pass without detecting which root cause triggered the refusal? [Precision, §VC-3, §VC-4, §STF-010] <!-- Evaluator: VC-3 tests PUID=0 alone and VC-4 tests PUID=1001 PGID=0, covering both causes (good). However VC-4 does not specify what error message should appear for PGID=0 specifically, so a test cannot distinguish "PGID=0 refusal" from a generic root refusal message that only mentions UID. If the entrypoint uses a generic message like "refusing to run as root", both VCs pass without validating that the PGID=0 code path was exercised. -->

- [ ] CHK010 Is the out-of-range boundary validation (PUID < 1 or > 4294967294) tested, or only the root-refusal boundary at 0? [Boundary Coverage, §Edge Cases, §STF-012] <!-- Evaluator: The edge cases specify script-level validation for values < 1 or > 4294967294, and STF-012 resolved that OS max is 4294967294 with script-level validation. No VC tests PUID=4294967295 (overflow), PUID=-1 (negative), or PUID=1 (lower valid boundary). The spec accepts "OS-level rejection" as acceptable, but script-level validation with "clear error message" is also specified. Without a test, the boundary between script-level and OS-level validation timing is unverified. -->

## Edge Case Coverage

- [ ] CHK011 Is the non-numeric validation tested with shell metacharacters ($, ;, \`, |, &&) to confirm injection prevention as claimed in the spec, or only with alphabetic strings ("abc")? [Security Coverage, §Edge Cases] <!-- Evaluator: The spec claims that non-numeric validation "also serves as injection prevention by rejecting shell metacharacters before values reach useradd/groupadd or shell expansion." Only alphabetic non-numeric values ("abc") are tested in VC-5. No test verifies rejection of shell metacharacters, leaving the injection prevention claim unvalidated. This is a critical gap if the entrypoint evaluates env vars in a context where metacharacters could be interpreted. -->

- [ ] CHK012 Is the existing-UID/GID reuse case (skip creation, reuse existing) tested to confirm that useradd/groupadd failures are handled gracefully and the existing user's shell and home directory are validated? [Coverage, §Edge Cases, §STF-006] <!-- Evaluator: The edge cases document that an existing UID reuses the existing user entry with validation of shell and home directory (per STF-006 resolution). No VC tests this scenario. An operator with a pre-existing system user at UID 1000 (e.g., if the container base image already defines a user at that UID) cannot verify the skip-creation logic works or that shell/home validation is enforced. Failure in this path would silently break assumptions about the running user's environment. -->

- [ ] CHK013 Is the concurrent-container chown race condition (STF-009) acknowledged as an untested gap in the test strategy, creating a documented risk acceptance for operators running multiple replicas? [Scope Control, §STF-009, §Plan §Testing Strategy] <!-- Evaluator: STF-009 documents the race condition ("Concurrent containers on the same volume race on chown; no lock mechanism is provided in v1") but the test strategy does not reference this limitation. An operator reading the test strategy would assume the feature is fully tested for production use with multiple replicas. The risk should be explicitly documented in the test strategy as a known untested scenario rather than buried in a stress-test finding. -->

- [ ] CHK014 Is the SIGTERM/SIGINT trap during chown tested with a timing-based test that sends SIGTERM mid-chown and verifies prompt exit without data corruption? [Coverage, §Operational Constraints, §STF-007, §Plan HINT-004] <!-- Evaluator: STF-007 and HINT-004 mandate signal handling with a trap before the chown phase. No test case verifies that the trap fires correctly, that partial chown is non-destructive, or that the container exits within the docker stop timeout (10s default). Without a timing-based integration test, the signal handling requirement is untestable against regressions — a future refactor that moves the trap after the chown call would not be caught by existing VCs. -->

- [ ] CHK015 Do the edge case tests cover the scenario where neither su-exec nor gosu is available, verifying the clear error message and non-zero exit per the spec's Edge Cases? [Coverage, §Edge Cases, §Plan §Error Handling Strategy] <!-- Evaluator: The edge cases specify that "Neither su-exec nor gosu available in PATH — entrypoint MUST fail with a clear error message." The test strategy has no scenario that removes both tools from PATH to verify this failure mode and the error message content. An implementation that silently falls back to bare `exec` (bypassing privilege drop entirely) would pass existing VCs while violating OR-005. -->

## Acceptance Criteria Completeness

- [ ] CHK016 Are SC-001 through SC-004 structured as measurable, automatable assertions with specific observable outcomes, or do they rely on imprecise language that requires human interpretation? [Measurability, §Spec §Success Criteria] <!-- Evaluator: SC-003 says "docker inspect shows the correct Entrypoint and Cmd." This is not specific about which entries constitute "correct" — a test would need additional spec reference or a known-good baseline to compare against. SC-001 says "creates files in /app/data owned by UID 1001" but does not specify whether this means files created by the running uvicorn process (post-startup) or the entrypoint itself, nor how to verify ownership of newly created files vs. pre-existing files. -->

- [ ] CHK017 Is there an acceptance criterion for the runbook requirements (RR-001, RR-002), or are documentation deliverables left unverified? [Completeness, §RR-001, §RR-002, §SC-004] <!-- Evaluator: SC-004 covers documenting PUID/PGID setup in docker-compose.yml, which partially covers RR-001. However RR-002 (documenting the temporary root execution window during entrypoint startup and explaining the accepted security tradeoff per the linuxserver.io pattern) has no corresponding success criterion. The root window documentation is a compliance requirement from the spec's own Compliance Check (§IV, Least-Privilege) but is not acceptance-tested. A delivery could pass all SC items while omitting RR-002. -->

- [ ] CHK018 Do the success criteria include a backward-compatibility regression test (SC-002) that runs the default-zero-config path and confirms identical behavior to the baseline image, including port binding, API response, and log output pattern? [Verifiability, §SC-002] <!-- Evaluator: SC-002 says "With no PUID/PGID set, the container starts and functions identically to the baseline." This is a behavioral equivalence claim without specifying what "functions identically" means in measurable terms. A regression test cannot determine whether the new image is "identical" without an explicit comparison protocol: which endpoints must respond, what log lines must appear, and what file ownership should look like under the default UID 1000 (vs. the previous fixed binocular user). -->

- [ ] CHK019 Does the test strategy include a multi-architecture assertion (at minimum confirming both linux/amd64 and linux/arm64 can build and run with the new entrypoint) per STF-013? [Coverage, §STF-013, §Plan §Target Platform] <!-- Evaluator: STF-013 documents that cross-arch integration testing is "recommended for CI" for su-exec availability and extreme UIDs. The plan targets "linux/amd64 + linux/arm64" but the test strategy never references multi-architecture verification. If su-exec is packaged for amd64 but not arm64 in the python:3.13-slim apt repositories (a documented risk), the gosu fallback path would only be tested on arm64 — but no CI scenario builds for arm64. The cross-arch gap is documented as a risk but not mitigated by a test. -->

- [ ] CHK020 Is the signal propagation chain (docker stop → entrypoint → exec su-exec → uvicorn) tested end-to-end with a timing assertion that docker stop completes within the configured stop timeout? [Coverage, §OR-005, §Plan HINT-002] <!-- Evaluator: OR-005 and HINT-002 emphasize correct signal propagation via exec, warning that without exec, docker stop hangs for 10s. No acceptance criterion or test case verifies this with a docker stop timing test. An implementation that accidentally omits exec (e.g., using bare `su-exec` without `exec`) would pass all VCs and SCs but cause a 10-second stop delay in production. The spec's operational constraint about sub-second signal propagation is not acceptance-tested. -->
