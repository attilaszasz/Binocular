## Architectural Learnings

### Validated Decisions

- **ADR-0001**: Single-container monolith with core/extension separation. Proven correct — no inter-service complexity, trivial deployment, single port.
- **ADR-0002**: Python 3.13 + FastAPI. Async I/O via `aiosqlite`/`httpx` handled concurrent checks well. `structlog` provided good observability.
- **ADR-0003**: React/Vite/Tailwind SPA served as static files. Multi-stage Docker build works cleanly. shadcn/ui (added in E030) was the right choice for component consistency.
- **ADR-0004**: SQLite + raw SQL + numbered migrations. Simple, reliable. WAL mode handled concurrent reads during scheduler writes. Pre-migration backups proved valuable.
- **ADR-0005**: Unsandboxed module engine with two-phase validation. AST static checks + runtime proof caught common errors pre-save. Error boundaries (`asyncio.wait_for`) contained module failures.
- **ADR-0006**: Centralized scraping client. Single enforcement point for robots.txt, rate limiting, and backoff worked as intended.
- **ADR-0007**: APScheduler + Apprise. In-process scheduling adequate for single-user. Notification deduplication (added in E028) was essential for usability.
- **ADR-0008**: Trusted-LAN security model. Optional basic auth + non-root + PUID/PGID covers the target audience.
- **ADR-0009**: Module-derived device type. Simplified the domain model and eliminated unnecessary DeviceType CRUD.
- **DDR-001–004**: All deployment decisions validated — multi-arch GHCR, homelab ops posture, SQLite backup via Online Backup API, PUID/PGID entrypoint.

### Revised Decisions

- **Frontend component strategy** evolved significantly: started with ad-hoc Tailwind, migrated to shadcn/ui in E030. V2 should start with shadcn/ui from day one.
- **Migration numbering** originally planned as per-epic non-overlapping ranges but ended up sequential. The 008 fix migration shows FK integrity must be validated after cross-epic refactors.
- **Module seeding** (E021) was not in the original plan but proved essential — users expect bundled modules to work out of the box without manual upload.

### Emergent Patterns

- **Feature-module decomposition** in frontend: `components/{inventory,logs,modules,settings,layout}/` emerged organically and should be the standard from the start.
- **Service layer pattern**: Backend services (checks, modules, inventory, scheduler, notifications, seeder, backup, email_renderer) encapsulate domain logic cleanly between routes and repositories.
- **Repository base**: Shared raw-SQL repository base with parameter binding works well; no ORM needed.
- **Build-time version injection**: `VITE_APP_VERSION` from git tag at Docker build time — simple, effective.
- **AI Module Kit as static assets**: Backend serves the kit files as static content; no additional dependencies needed.

## Scope Refinements

### Over-Scoped

- **Standalone DeviceType entity** (E005): Proved unnecessary; device type should be derived from linked module from the start (ADR-0009 added in E022).
- **Separate per-device-type schedule config page**: Per-module frequency editing on the Modules page (E026) was sufficient; no need for a separate settings surface.

### Under-Scoped

- **Email notification design**: Plain-text was insufficient; responsive HTML email (E027) should have been part of the original notification epic.
- **Notification deduplication**: Alert fatigue from repeated same-version notifications was an obvious gap that should have been in the original CAP-007.
- **UI component consistency**: Starting with ad-hoc Tailwind created debt that required a full migration (E030). Should start with a component library.
- **Collapsible navigation**: Screen real estate on smaller displays needed attention earlier.

### Missing Capabilities

- No new capabilities identified that aren't already covered in the prototype. The E031 AI-assisted authoring closed the last gap.

## Operational Learnings

- Docker multi-stage build (Node→Python) works reliably for the single-image strategy.
- PUID/PGID entrypoint via `su-exec` solves the most common homelab support issue (volume permissions).
- `compose.yaml` + `.env.example` is the right distribution format for self-hosters.
- Scheduled backup job (APScheduler) with `VACUUM INTO` is reliable for live-safe SQLite backups.
- Version injection via `VITE_APP_VERSION` at build time is clean and doesn't require runtime lookups.

## Risk Reductions

- **Scraper breakage risk**: Mitigated by honest failure status and fixture-based validation — confirmed working.
- **ACE trust boundary**: Documented and accepted; non-root + PUID/PGID + error boundary in place.
- **Notification reliability**: HTML email rendering + deduplication + delivery failure logging all implemented.
- **Data loss risk**: Pre-migration backups + scheduled backup job + restore runbook in place.
- **False negatives**: Zero false positives/negatives for all 4 shipped modules against captured fixtures.
