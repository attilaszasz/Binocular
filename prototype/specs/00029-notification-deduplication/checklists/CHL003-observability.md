# Observability Requirements Quality Checklist: Notification Deduplication

**Domain**: Observability | **Depth**: Standard | **Audience**: Reviewer
**Focus Areas**: Logging completeness, structured log fields, error visibility, dedup decision auditability, operational visibility

---

## Logging Completeness

- [X] CHK001 Does FR-009 require logging the full comparison context — including `current_version` and the `compare_versions()` result (newer/equal/older) alongside `latest_version` and `last_notified_version` — or does it only mandate a binary decision log that strips the reasoning from which the operator could reconstruct the comparison? [Completeness, Spec §FR-009, Data-Model §Dedup Gate Logic] <!-- Evaluator: Covered by spec.md §FR-009 + data-model.md §Validation Rules. FR-009 requires logging latest_version, last_notified_version, and decision. The operator can reconstruct comparison reasoning from the two version values (equal when both are "2.0", older when latest="1.5" and last_notified="2.0"). current_version is outside the dedup gate scope (it compares latest vs last_notified, not latest vs current). The binary decision with version values provides sufficient auditability. -->

- [ ] CHK002 Is logging required for the entire dedup check lifecycle — check started, `last_notified_version` read, dedup evaluation, dispatch attempt (with per-channel results), `last_notified_version` update outcome, and check completed — or does the spec only require logging the single dedup decision point, leaving the operator unable to trace a device's full check execution across log lines? [Completeness, Spec §FR-004, Spec §FR-005, Plan §Error Handling Strategy] <!-- Evaluator: ASK — Genuinely unresolved. FR-009 covers dedup decisions; plan Error Handling covers failures; new FR-010 covers check initiation; new FR-011 covers state transitions. Gaps remain: last_notified_version read, dispatch attempt start, check completed. Options: (A) Log check_started + check_completed as INFO bookends with check-run correlation ID — enables full trace; (B) Log only the decision (FR-009) + failures (plan) + init/transition (FR-010/FR-011) — sufficient for most audits; (C) No lifecycle logging beyond existing artifacts. RECOMMENDED: Option B (current coverage is adequate). -->

- [X] CHK003 When `compare_versions()` raises a `VersionComparisonError` on an invalid `last_notified_version` string, does the spec require logging the offending version string, the module identifier, and the exception type — or does the data-model's "Treat as NULL, log error" instruction leave the log content unspecified, making post-mortem diagnosis dependent on source-code inspection? [Completeness, Data-Model §Validation Rules, Plan §Error Handling Strategy] <!-- Evaluator: Resolved — amended plan.md Error Handling Strategy row "Invalid last_notified_version string" to specify logging device_id, last_notified_version (raw string), exception_type, and module_id. -->

- [X] CHK004 Is there a logging requirement for the case where zero notification channels are configured, so the operator can distinguish "device had no channels at check time" from "channels existed but all failed"? [Completeness, Spec §Edge Cases, Plan §Error Handling Strategy] <!-- Evaluator: Resolved — amended plan.md Error Handling Strategy row "Zero configured channels" to require logging at WARNING level with device_id and reason="zero_channels_configured". -->

- [ ] CHK005 When the dedup gate suppresses a notification, is the operator able to see in logs *when* the original notification for that version was dispatched, or is the suppression log entry isolated from the notification history, forcing the operator to grep through historical logs to find the prior dispatch event? [Debuggability, Spec §FR-009, Spec §US1] <!-- Evaluator: ASK — Genuinely unresolved. FR-009 logs latest_version and last_notified_version but no reference to the prior dispatch event (timestamp, check-run ID). The operator can grep historical logs for device_id + version to find the prior dispatch, albeit with manual effort. Options: (A) Add last_notified_at timestamp field to devices table and include in suppression log — enables quick lookup; (B) Add prior_check_run_id to FR-009 log fields — requires implementing check-run IDs; (C) Accept current state — operator can grep historical logs by device_id + version. RECOMMENDED: Option C (acceptable; grep is straightforward for single-user deployments with 5-50 devices). -->

## Structured Log Fields

- [X] CHK006 Does FR-009 mandate structured logging with machine-parseable key-value pairs (consistent with the project's structlog usage per the plan), or could an implementation emit an unstructured plain-text message like "Suppressed notification for device 42: version 2.0 already notified" that resists automated filtering, alerting, and dashboarding by log aggregation tools? [Completeness, Spec §FR-009, Plan AD-004, Data-Model §Validation Rules] <!-- Evaluator: Resolved — amended spec.md FR-009 to require "structured key-value pairs (using structlog)." Plan AD-004 and data-model §Validation Rules already reference structlog patterns; FR-009 now explicitly mandates structured format, closing the gap between spec and plan. -->

- [X] CHK007 Are the log field names for deduplication events standardized and documented — e.g., `device_id` vs `device`, `latest_version` vs `detected_version`, `decision` vs `action` — or is each log-emitting code path free to choose its own field naming, producing structurally heterogeneous log entries that defeat structured log querying? [Consistency, Spec §FR-009, Data-Model §Validation Rules, Plan §Error Handling Strategy] <!-- Evaluator: Covered by data-model.md §Validation Rules. The FR-009 validation rule provides canonical field names via the structlog.info(...) example: device_id, latest_version, last_notified_version, decision, trigger. The plan's Error Handling Strategy entries (now amended) reference device_id and consistent field names. The data-model serves as the authoritative field name registry for the implementation. -->

- [X] CHK008 Does the spec require logging the check trigger source (scheduled vs manual) as a structured field in the dedup decision log, enabling the operator to satisfy SC-002's audit requirement that "manual and scheduled checks produce identical deduplication behavior" without comparing separate log streams? [Debuggability, Spec §SC-002, Spec §FR-006] <!-- Evaluator: Resolved — amended spec.md FR-009 to include `trigger` (scheduled|manual) field in the dedup decision log. Also added FR-010 requiring check initiation logging with trigger source. SC-002 auditability is now achievable from a single log query. -->

- [ ] CHK009 Is there a requirement to include a correlation identifier (check-run ID, trace ID, or request ID) in all log entries produced within a single device check execution, so that the dedup decision, dispatch attempt, channel results, and `last_notified_version` update can be stitched together as a single trace? [Operability, Spec §FR-004, Plan §Error Handling Strategy] <!-- Evaluator: ASK — Genuinely unresolved. No correlation ID concept exists in the spec or plan. A single device check can produce multiple interleaved log lines in concurrent environments. Options: (A) Generate a UUID per check run and include as check_run_id in all related log entries — enables full trace stitching; (B) Rely on device_id + timestamp ordering for correlation (sufficient for single-user, 5-50 device deployments with serialized per-device locking); (C) Defer to future structured tracing adoption. RECOMMENDED: Option B (device-level locking + timestamps provide adequate correlation for current scale; avoid premature complexity). -->

## Error Visibility

- [X] CHK010 When all configured notification channels fail during a dispatch attempt, does the spec require logging *which* channels failed and *why* (transport error message, HTTP status code, Apprise exception type) — or does the plan's "log warning" instruction leave operators with only a generic failure indicator, making per-channel failure diagnosis impossible without reproducing the failure in a test environment? [Actionability, Spec §FR-005, Plan §Error Handling Strategy] <!-- Evaluator: Resolved — amended plan.md Error Handling Strategy row "All channels fail" to require logging device_id, failed_channels (list of channel names), and per-channel failure reasons (transport error message, HTTP status code, exception type). -->

- [X] CHK011 When one channel succeeds and another fails (partial dispatch success), does the spec require logging the failed channel's identity, failure reason, and the fact that `last_notified_version` was still updated because at least one channel succeeded — or is the partial failure silently absorbed into the success path, leaving the operator unaware that a backup channel is broken? [Actionability, Spec §FR-004, Plan §Error Handling Strategy] <!-- Evaluator: Resolved — amended plan.md Error Handling Strategy row "Partial channel failure" to require logging warning with device_id, failed_channel name, and failure reason (transport error message, HTTP status code, exception type). -->

- [ ] CHK012 When `BEGIN IMMEDIATE` serialization causes a check to wait on another check's lock, is lock acquisition latency or contention logged, enabling the operator to detect when the deduplication locking strategy becomes a throughput bottleneck at scale? [Operability, Spec §FR-008, Data-Model §Locking Strategy] <!-- Evaluator: ASK — Genuinely unresolved. Neither spec nor plan requires lock wait time logging. At 5-50 devices with serialized per-device locking, contention is unlikely to be a practical bottleneck. Options: (A) Add DEBUG-level log recording lock acquisition duration for transactions exceeding a threshold (e.g., 500ms); (B) No lock timing logging — acceptable for single-user deployment scale; (C) Add structured metrics (Prometheus histogram). RECOMMENDED: Option B (scale doesn't justify lock timing instrumentation; operator can use SQLite profiling tools if needed). -->

- [X] CHK013 Does the spec require structured error logging when `compare_versions()` encounters an unparseable firmware version (unexpected format, corrupt string, encoding error), including the module identifier, raw version string, and the check context — or does the plan's "Record as check_failed; do not update last_notified_version" direction treat the version-comparison error as a generic check failure indistinguishable from a network error or module crash? [Actionability, Plan §Error Handling Strategy, Spec §Assumptions] <!-- Evaluator: Resolved — amended plan.md Error Handling Strategy row "version_compare error" to require logging error with device_id, module_id, raw_version_string, exception_type, and exception_message. -->

- [ ] CHK014 Is there a requirement to log at ERROR or WARNING level when the dedup gate encounters an edge case that silently changes behavior — such as a `last_notified_version` containing a value that is syntactically valid but semantically nonsensical (empty string, "0.0.0", a git SHA) — so the operator can detect and correct data anomalies before they cause missed or duplicate notifications? [Actionability, Spec §Edge Cases, Data-Model §Post-Migration Column Constraints] <!-- Evaluator: ASK — Genuinely unresolved. No anomaly detection logging exists. The data-model allows free-text version strings; semantically invalid values (e.g., "abcdef", empty string) would produce indeterminate comparison results depending on compare_versions() implementation behavior. Options: (A) Add a WARNING-level log entry when compare_versions() returns an "indeterminate" result for a non-NULL last_notified_version, flagging potential data corruption; (B) Add a startup validation query that checks all last_notified_version values against known version format patterns; (C) Accept current state — compare_versions() handles malformed strings gracefully per its existing behavior. RECOMMENDED: Option C (compare_versions() already handles edge cases; adding semantic validation is out of scope for this feature). -->

## Dedup Decision Auditability

- [X] CHK015 When `last_notified_version` is updated (a successful dispatch has occurred), does the spec require logging the transition with the old value, new value, device ID, and timestamp — creating an audit trail of notification state changes that survives log rotation and allows the operator to reconstruct the notification history for any device without querying the live database? [Auditability, Spec §FR-004, Data-Model §Write Semantics] <!-- Evaluator: Resolved — added FR-011 to spec.md requiring structured INFO-level logging of last_notified_version state transitions with device_id, previous_value, new_value, and trigger. Added corresponding validation rule to data-model.md. This creates a durable audit trail independent of the single-column database state. -->

- [X] CHK016 Does the spec require that every dedup suppression event be logged even when the suppression is the "correct" behavior — i.e., logging *all* suppression decisions, not only anomalous ones — so that an operator querying the log can confirm that the system is actively checking devices and correctly suppressing duplicates, rather than silently failing to check at all? [Auditability, Spec §FR-009, Spec §US1 Acceptance Scenario 4] <!-- Evaluator: Covered by spec.md §FR-009. FR-009 requires logging all deduplication decisions with both "suppressed" and "dispatched" outcomes. Combined with new FR-010 (check initiation log), the operator has positive confirmation (check_initiated + decision=suppressed) that a check ran and the dedup gate evaluated correctly, distinguishing from a silent check failure. -->

- [X] CHK017 Are the dedup decision log entries timestamped with sufficient precision (millisecond or microsecond) to allow the operator to order decisions chronologically when concurrent checks on the same device produce multiple log lines, verifying that the serialization lock (FR-008) correctly ordered the decisions? [Testability, Spec §FR-008, Spec §SC-001] <!-- Evaluator: Covered by existing structlog infrastructure. structlog's default ISO 8601 timestamps include millisecond precision, which is sufficient for ordering decisions. The project's existing logging configuration provides this without an explicit spec requirement. -->

- [X] CHK018 When a device transitions from having a NULL `last_notified_version` to having a value after the first-ever successful dispatch, does the spec require logging this as a distinct event (e.g., `decision="first_dispatch"` rather than `decision="dispatched"`) — enabling the operator to detect when a device's notification state is being established for the first time, which has different operational significance than a routine re-notification for a newer version? [Auditability, Spec §FR-003, Data-Model §State Transition Diagram] <!-- Evaluator: Covered by existing FR-009 + new FR-011. The FR-009 decision log includes last_notified_version=NULL for first-ever dispatch, which is distinguishable from last_notified_version="2.0" (re-notification). The new FR-011 state-transition log also captures NULL → version transitions explicitly. No separate decision enum value needed — the NULL value in the structured log already distinguishes the event. -->

## Operational Visibility

- [X] CHK019 Is there a requirement to emit a startup or migration-complete log entry confirming the `devices.last_notified_version` column was added and initialized (all rows NULL) — giving the operator positive confirmation that the deduplication feature is deployed and active, rather than assuming the migration succeeded because the application started without error? [Operability, Spec §Implementation Signals, Data-Model §Schema Change] <!-- Evaluator: Resolved — added startup signal requirement to data-model.md §Schema Change: on application startup after migration, log structlog.info("notification_deduplication_active", ...) with migration number and existing device count. -->

- [X] CHK020 When a manual on-demand check is initiated by the operator, does the spec require logging that the check request was received (with device ID and trigger source) *before* the dedup gate evaluation — so that if the gate suppresses the only observable side effect (the notification), the operator still has a log trace proving the manual check was actually executed? [Operability, Spec §US2, Spec §FR-006] <!-- Evaluator: Resolved — added FR-010 requiring INFO-level check initiation logging with device_id and trigger before dedup gate evaluation. Combined with FR-009 (decision log), the operator now has check_initiated + decision=suppressed confirming execution even when no notification is dispatched. -->

- [ ] CHK021 Does the spec require exposing deduplication metrics — counters for notifications_dispatched, notifications_suppressed, dispatch_attempts_failed — as application-level instrumentation (e.g., Prometheus counters or structured log metrics) enabling operators to monitor dedup health over time without parsing INFO-level log streams? [Operability, Spec §Success Criteria, Plan §Performance Goals] <!-- Evaluator: ASK — Genuinely unresolved. No metrics requirement exists in spec or plan. The structured log approach (FR-009 + FR-010 + FR-011) enables log-based metrics via aggregation tools (Loki LogQL, ELK), but requires operator setup. Options: (A) Add Prometheus counter instrumentation (prometheus_client) for notifications_dispatched, notifications_suppressed, dispatch_failures — enables out-of-box monitoring; (B) Rely on structured logs for metrics — operator configures their own log aggregation; (C) Add periodic INFO-level summary log line with aggregate counts (see CHK022). RECOMMENDED: Option B (keep simple; structured logs are already machine-parseable for aggregation tools; avoid adding Prometheus dependency for a single-user tool). -->

- [ ] CHK022 When a scheduled check cycle runs for multiple devices, does the spec require logging a batch-completion summary — devices checked, notifications dispatched, notifications suppressed, errors encountered — giving the operator a single-line operational snapshot of the check cycle without tallying per-device log lines? [Operability, Spec §User Scenarios, Plan §Project Structure] <!-- Evaluator: ASK — Genuinely unresolved. No batch summary requirement exists. With FR-009/FR-010/FR-011 providing per-device structured logs, operators can use aggregation tools for cycle-level summaries. Options: (A) Add INFO-level batch summary log at end of scheduled check cycle with devices_checked, notifications_dispatched, notifications_suppressed, errors, duration_ms; (B) Rely on structured per-device logs + operator aggregation; (C) Defer to metrics solution (see CHK021). RECOMMENDED: Option B (structured per-device logs are sufficient for 5-50 device scale; adding batch summary is a convenience feature). -->

- [X] CHK023 Is there a requirement to log the `last_notified_version` field in the device API response or device detail page, or is the field only persisted in the database and included silently in API JSON — making it invisible to an operator who does not inspect raw API responses or query the database directly? [Debuggability, Spec §Key Entities, Spec §Clarifications] <!-- Evaluator: Covered by spec.md §Key Entities ("Exposed in the Device API response and visible in the UI on the device detail view") and Clarifications Q4 ("Expose in both API response and UI device detail view"). This is a UI/API visibility requirement, not a logging requirement per se. The spec adequately addresses operator visibility of the field. -->

- [X] CHK024 Does the spec require distinguishing in logs between "suppressed because latest_version equals last_notified_version" and "suppressed because latest_version is older than last_notified_version" — two semantically different outcomes that the binary decision field collapses, hiding the user-downgrade-firmware edge case from operational visibility? [Debuggability, Spec §Edge Cases, Spec §FR-002, Data-Model §Dedup Gate Logic] <!-- Evaluator: Covered by existing FR-009 log fields. The log includes both latest_version and last_notified_version as structured fields. When decision="suppressed" and latest_version="2.0" + last_notified_version="2.0", the operator knows it was equal. When latest_version="1.5" + last_notified_version="2.0", the operator knows it was older (downgrade). The comparison result is derivable from the logged version values. FR-002 and spec Edge Cases already document the downgrade scenario. -->

- [ ] CHK025 Does the spec require INFO-level logging of the `BEGIN IMMEDIATE` transaction boundaries (lock acquisition and release) when the transaction duration exceeds a threshold — allowing operators to correlate long-running dedup transactions with check latency and detect when version-compare or notification dispatch inside the lock window causes contention? [Operability, Data-Model §Locking Strategy, Plan HINT-002] <!-- Evaluator: ASK — Genuinely unresolved. Neither spec nor plan requires transaction duration logging. Lock duration is bounded by the scope of the transaction (dedup read + gate + dispatch + write). Options: (A) Add DEBUG-level log of transaction duration when exceeding a threshold (e.g., 500ms); (B) No transaction timing logging — lock contention is unlikely at 5-50 devices with serialized per-device locks; (C) Defer to external SQLite profiling. RECOMMENDED: Option B (transaction scope is well-bounded; adding timing logging is premature for current scale). -->
