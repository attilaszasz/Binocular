# Checklist: Performance — Collapsible Menu & Version Display

## CSS Transition Performance

- [X] CHK080 Are the CSS transition properties for the sidebar width change explicitly specified as property-targeted (`transition-[width]`) rather than blanket `transition-all`, to minimise layout-thrash risk on child elements during animation? [Completeness, Plan §HINT-003, Research §React Collapsible Sidebar]
- [X] CHK081 Are the transition timing values (`duration-300 ease-in-out`) applied consistently to both the sidebar width transition AND the main-content margin-left transition so they animate in lockstep without compounding reflow? [Consistency, Spec §SC-001, §FR-001]
- [X] CHK082 Does the spec or plan acknowledge that `transition-[width]` still triggers the full Layout → Paint → Composite pipeline (not just Composite, unlike `transform`), and is this performance characteristic explicitly accepted? [Completeness, Research §React Collapsible Sidebar, Plan §Performance Goals]
- [X] CHK083 Does the spec define how the two simultaneous layout-triggering transitions (sidebar width + content margin-left) avoid compounding per-frame reflow cost — e.g., by relying on the browser's coalescing of style recalc within the same animation frame? [Completeness, Spec §FR-001, Q009]
- [X] CHK084 Are all transition classes gated behind the `md:` breakpoint so the animation engine is not invoked on viewports <768px where collapsible behaviour is disabled? [Consistency, Spec §FR-001, STF-001]
- [X] CHK085 Does the spec or plan require the `motion-safe:` Tailwind variant (already noted as a reuse pattern) to respect `prefers-reduced-motion`, preventing the sidebar transition from causing discomfort or violating user OS accessibility settings? [Completeness, Plan §Brownfield Notes §Patterns to reuse]
- [X] CHK086 Does the spec define the animation-level debounce mechanism (CSS transition overlap absorption) in sufficient detail to distinguish it from a JavaScript debounce/throttle, clarifying that rapid toggles are handled by the browser's native transition interruption rather than a custom timing function? [Clarity, Spec §Edge Cases]
- [X] CHK087 Is the browser's composite-layer promotion strategy for the sidebar `<aside>` addressed — i.e., does the spec consider whether `will-change: width` or `contain: layout style` is needed to isolate the sidebar's reflow scope from the rest of the page during animation? [Completeness, Spec §Key Entities, Plan §Performance Goals]

## Rapid Toggle Debouncing

- [X] CHK088 Is "rapid repeated toggle clicks" defined with a quantitative threshold (e.g., inter-click interval < animation duration, or ≥5 clicks within 500ms) so the acceptable-vs-janky boundary is testable and unambiguous? [Clarity, Spec §Edge Cases]
- [X] CHK089 Does the spec specify whether an in-flight transition should be interrupted and reversed on a new toggle (browser-native behaviour for CSS transitions) or queued to complete before the next toggle is processed? [Completeness, Spec §Edge Cases]
- [X] CHK090 Does the spec or plan require the functional updater pattern (`setIsCollapsed(prev => !prev)`) to prevent stale-state bugs when the collapse state is read and written within the same event cycle during rapid toggles? [Completeness, Spec §Edge Cases, Plan §AD-001]
- [X] CHK091 Does the spec define a minimum acceptable frame rate or jank budget during the toggle animation (e.g., ≥55fps, or ≤10ms frame budget per RAIL) to make the "no glitch" requirement objectively verifiable? [Measurability, Spec §Edge Cases, Plan §Performance Goals]
- [X] CHK092 Does the spec address whether the tooltip show/hide logic (200-300ms delay, DOM mutation) is suspended during an active collapse/expand transition to prevent concurrent timer callbacks from causing mid-animation re-renders or frame drops? [Completeness, Spec §FR-003, §Edge Cases]
- [X] CHK093 Does the spec define whether nav-item label visibility toggling (FR-002) — removing/adding class-based `hidden` — is batched into the same frame as the width transition to avoid an extra forced layout pass on every toggle? [Completeness, Spec §FR-002, §FR-001]
- [X] CHK094 Does the spec address the impact of rapid toggles on localStorage write frequency — specifically, whether each rapid toggle triggers a synchronous blocking write, and whether this is acceptable within the animation frame budget? [Completeness, Spec §FR-006, §Edge Cases]

## localStorage Read/Write Performance

- [X] CHK095 Does the spec constrain localStorage reads to exactly once — via a lazy `useState` initialiser — rather than on every render, in a `useEffect` that causes a double render, or via repeated `getItem` calls during the component lifecycle? [Completeness, Spec §FR-006, Plan §AD-001]
- [X] CHK096 Does the spec limit localStorage writes to exactly one per toggle action with no additional middleware (e.g., no write to `sessionStorage` as backup, no meta-data writes), keeping synchronous I/O to the minimum necessary? [Completeness, Spec §FR-006]
- [X] CHK097 Does the spec explicitly acknowledge that `localStorage.setItem` and `getItem` are synchronous and block the main thread (per HTML spec §Storage API), and does it specify how the ~1-5ms blocking cost per operation fits within the 10ms RAIL frame budget? [Completeness, Spec §FR-006, Research §localStorage, Plan §Performance Goals]
- [X] CHK098 Does the spec define whether the try-catch wrapper for localStorage access should be scoped narrowly around only the storage call (not the entire toggle handler) to avoid V8 JIT deoptimisation of the hot toggle path? [Completeness, Spec §FR-006, STF-003]
- [X] CHK099 Does the spec specify the serialisation format for the localStorage value — a raw `"true"`/`"false"` string rather than a JSON-stringified boolean — avoiding unnecessary `JSON.parse`/`JSON.stringify` overhead on every read/write? [Completeness, Spec §FR-006]
- [X] CHK100 Does the spec define a maximum write frequency or a cooldown interval for localStorage writes to guard against potential `QuotaExceededError` or excessive synchronous I/O from automation scripts or test frameworks rapidly toggling the sidebar? [Completeness, Spec §FR-006, Plan §Scale/Scope]

## React Re-render Optimization

- [X] CHK101 Does the spec or plan constrain the re-render scope of the collapse state change — i.e., does the architecture ensure that only the sidebar subtree re-renders on toggle, rather than the entire app layout? [Completeness, Plan §Architecture, §AD-001]
- [X] CHK102 Does the spec or plan require the lazy `useState` initialiser pattern (synchronous localStorage read at init) as the exclusive approach, excluding alternatives (`useEffect` + second render, context-based init) that would cause an unnecessary additional render cycle? [Completeness, Plan §AD-001]
- [X] CHK103 Does the spec require `React.memo` or equivalent optimisation for the nav-item list to prevent full re-rendering of all nav items when only the collapse state (which affects their label-visibility class) changes? [Completeness, Spec §FR-002, Plan §Architecture]
- [X] CHK104 Does the spec address whether the 200-300ms `setTimeout` for tooltip appearance triggers a React re-render mid-transition, and is there a requirement to cancel this timer on toggle to prevent memory pressure or stale-state callbacks? [Completeness, Spec §FR-003, §Edge Cases]
- [X] CHK105 Is the VersionDisplay component's re-render behaviour specified — given its content is a compile-time constant string with no reactive dependencies, should it be extracted as a pure component (e.g., `React.memo` or static markup) to avoid re-rendering on every collapse toggle? [Completeness, Spec §FR-004]
- [X] CHK106 Does the spec define whether tooltip DOM elements are created on each hover and destroyed on dismiss (GC churn on every interaction) or rendered once and visibility-toggled, and is the chosen strategy acceptable for the expected number of nav items? [Completeness, Spec §FR-003, §Assumptions]
- [X] CHK107 Does the spec define a maximum expected nav-item count (matching E003's existing structure) so the tooltip system's per-item overhead — timer creation, DOM insertion, event listeners — has a bounded performance budget? [Completeness, Spec §Assumptions, Plan §Technical Context]
- [X] CHK108 Does the Key Entities "transitioning" state require a JavaScript state variable that triggers an additional re-render on every toggle, or is "transitioning" purely a CSS-class concern (no JS state, no extra render)? [Clarity, Spec §Key Entities]

## Cross-cutting Performance Coverage

- [X] CHK109 Does the spec define a measurable INP (Interaction to Next Paint) or responsiveness budget for the toggle interaction (e.g., ≤100ms main-thread blocking, ≤200ms INP per Web Perf WG recommendations)? [Measurability, Spec §Plan §Performance Goals, Research §RAIL]
- [X] CHK110 Does the spec define whether the `hidden` class toggle on nav-item labels (FR-002) uses `display: none` (which triggers forced layout recalculation) or `visibility: hidden` (which only triggers repaint), and is the performance characteristic of the chosen approach stated? [Completeness, Spec §FR-002]
- [X] CHK111 Does the spec specify a maximum acceptable DOM-node count increase between expanded and collapsed states, bounding the tooltip system's upper memory allocation? [Completeness, Spec §FR-003]
- [X] CHK112 Does the spec define a performance validation criterion — e.g., "toggle animation must complete at ≥55fps on Chrome 120+/Firefox 120+ at 1920×1080 on a mid-range desktop (Intel i5-12400 / 16GB RAM)" — making the "smooth transition" requirement in SC-001 objectively verifiable? [Measurability, Spec §SC-001, Plan §Performance Goals]
- [X] CHK113 Does the spec address whether the sidebar `<aside>` element uses CSS `contain: layout style` to limit the reflow/repaint scope of the width animation to only the sidebar subtree, preventing the rest of the page from being re-laid-out on every animation frame? [Completeness, Spec §Key Entities, Plan §Performance Goals]
- [X] CHK114 Does the spec consider the performance impact of the version-display tooltip (FR-004) in collapsed state — specifically, whether it creates a second tooltip instance (doubling DOM/timer overhead) or shares the same tooltip component as nav items? [Completeness, Spec §FR-004, §FR-003]
- [X] CHK115 Are all performance-related plan elements — HINT-003 (transition property targeting), AD-001 (lazy initializer avoids double render), Performance Goals line — consistently reflected in the spec's requirements and success criteria? [Traceability, Plan §HINT-003, §AD-001, §Performance Goals; Spec §FR-001, §SC-001, §Edge Cases]
- [X] CHK116 Does the spec define whether the `duration-300` transition timing class should use Tailwind's `transition` shorthand or explicit `transition-property`, `transition-duration`, and `transition-timing-function` utilities for clearer performance intent? [Clarity, Plan §HINT-003, Spec §SC-001]
