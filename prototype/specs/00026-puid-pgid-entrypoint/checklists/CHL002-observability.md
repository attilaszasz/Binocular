# Observability Requirements Quality Checklist: PUID/PGID Entrypoint

**Domain**: Observability | **Depth**: Standard | **Audience**: Reviewer
**Focus Areas**: Logging Format & Sink, Signal Handling Visibility, Startup Timing, Failure Visibility, Operator Debuggability

---

## Logging Format & Sink

- [ ] CHK001 Does OR-006 specify a structured logging format (timestamp, severity level, machine-parseable key-value pairs) for warning messages, or is the output unstructured plain text that prevents automated log aggregation and alerting? [Completeness, §OR-006, §Clarifications] <!-- Evaluator: The clarification says "Warnings to stderr with descriptive message including var name and value" but does not specify a format. Without a consistent structure (e.g., `[entrypoint] WARNING: PUID="abc" is non-numeric, falling back to 1000`), operators cannot reliably filter, parse, or alert on entrypoint warnings in centralized logging systems (Loki, ELK, Datadog). The lack of a logging format requirement means each implementer may choose a different format, making future log-based tooling fragile. -->

- [ ] CHK002 Are informational startup events (env var resolution, user/group creation outcome, chown start/completion) emitted to the log stream, or is only error/warning output specified, leaving operators with no trace of successful configuration? [Completeness, §Plan §Testing Strategy, §Spec §Operational Constraints] <!-- Evaluator: OR-006 only mandates logging for non-numeric values. No requirement exists for logging normal startup progression (e.g., "PUID=1001, PGID=1001 resolved", "user 'app' created", "chown /app/data complete"). Operators debugging a startup hang or volume ownership issue have no positive logging to confirm each phase completed. A silent startup gives no diagnostic foothold when something goes wrong after the entrypoint finishes. -->

- [ ] CHK003 Does the spec ensure all entrypoint output (info, warning, error) goes to a consistent sink (stderr per OR-006), and is this consistently documented across all requirements and edge cases? [Consistency, §OR-006, §Plan §AD-003] <!-- Evaluator: OR-006 specifies stderr for warnings. However the spec does not specify the output sink for hard-error messages (root refusal, chown failure, out-of-range, missing su-exec). If error messages go to stdout while warnings go to stderr, operators relying on stderr-based alerting pipelines would miss fatal errors. The plan's Error Handling Strategy table documents exit behavior but not the output sink for each category. -->

## Signal Handling Visibility

- [ ] CHK004 Is the SIGTERM/SIGINT trap behavior observable to the operator (e.g., a log line "Received SIGTERM, interrupting chown") or does the trap exit silently, leaving operators unable to distinguish a clean shutdown from an abort during chown? [Debuggability, §Spec §Operational Constraints, §STF-007] <!-- Evaluator: The operational constraints and STF-007 resolution mandate a trap for SIGTERM/SIGINT before the chown phase to ensure prompt shutdown, but do not require logging the signal receipt. An operator running `docker stop` during a large-volume chown would see no output indicating the trap fired, making it impossible to confirm the container shutdown promptly rather than hanging on the signal. Observable trap logging would also assist debugging of docker stop timeout issues. -->

- [ ] CHK005 Does the spec require logging when a partial chown occurs due to signal interruption, so the operator can detect that volume ownership may be incomplete and investigate? [Completeness, §STF-007, §STF-011] <!-- Evaluator: The spec acknowledges "partial chown on SIGTERM is accepted" but does not require logging the partial state. An operator restarting after a signal-interrupted chown has no indication that some files may still have wrong ownership. Without a log line like "WARNING: chown interrupted by SIGTERM — /app/data may have incomplete ownership", operators are unaware of a potential permission inconsistency on the next start. -->

- [ ] CHK006 Is the signal propagation chain from docker stop through exec su-exec to uvicorn documented as verifiable by the operator, or is the chain untestable at runtime until a 10-second timeout occurs? [Testability, §OR-005, §Plan HINT-002] <!-- Evaluator: OR-005 mandates exec for signal propagation, and HINT-002 warns that without exec, docker stop hangs for 10s. However no requirement specifies that uvicorn's signal handling is verifiable (e.g., by checking that uvicorn's PID equals the container PID 1 or by observing uvicorn's graceful-shutdown log line in response to docker stop). An operator cannot confirm correct signal propagation without reading the entrypoint source code or performing an ad-hoc timing test. -->

## Startup Timing

- [ ] CHK007 Does the spec provide a measurable startup time objective across volume sizes, or is the <2s target (from plan) aspirational without a verifiable acceptance criterion? [Testability, §Plan §Performance Goals, §STF-011] <!-- Evaluator: The plan states "Startup time < 2s for typical volumes (<10k files)" but this is not reflected in any success criterion or verification criterion. SC-001 through SC-004 contain no startup timing requirement. Operators with volumes exceeding 10k files have no performance commitment to validate against, and there is no way to determine whether an implementation meets or violates the performance goal because it was never codified as a testable assertion. -->

- [ ] CHK008 Is chown duration instrumentation required so operators with large volumes can distinguish slow startup from container failure (hang or deadlock)? [Debuggability, §Operational Constraints §STF-011] <!-- Evaluator: The spec documents that chown scales linearly with file count, but requires no timing log for the chown phase. An operator whose container takes 60s to start has no log line indicating "chown /app/data completed in 58s" vs "container is stuck after phase X." Without phase-level timing, diagnosing startup performance regression requires external profiling, which contradicts the set-and-forge operability promise. -->

- [ ] CHK009 Does the entrypoint log the resolved UID:GID and username on every start, giving operators a positive confirmation of identity before the CMD executes? [Debuggability, §VC-1, §OR-001, §OR-002] <!-- Evaluator: VC-1 verifies that "a user with UID 1001 and GID 1001 exists and owns /app/data and /app/modules, and uvicorn runs as UID 1001:GID 1001 with username app." But the spec does not require the entrypoint to log this resolution at startup. An operator seeing a permission error must infer from context whether the correct identity was established. A startup log line like "Running as UID 1001 (app), GID 1001" would provide immediate confirmation. -->

## Failure Visibility

- [ ] CHK010 Do hard-error exit messages include actionable context (offending variable, resolved value, attempted path) enabling the operator to diagnose and correct the issue without reading the entrypoint source? [Actionability, §OR-003, §OR-004, §Plan §Error Handling Strategy] <!-- Evaluator: OR-003 says "exit with a non-zero code and clear error message" and OR-004 says "log path" on chown failure. However the spec does not require that root-refusal messages name the offending variable (PUID=0 vs PGID=0) to guide the operator's fix, or that chown-failure messages include the specific path that failed. An operator seeing "ERROR: refusing to run as root" does not know which variable to correct, and must infer from context or read the entrypoint source. -->

- [ ] CHK011 Are distinct non-zero exit codes assigned per failure mode (root refusal, missing su-exec, chown failure, out-of-range) to enable automated health monitoring to differentiate fatal error types? [Operability, §Plan §Error Handling Strategy, §Spec §Operational Requirements] <!-- Evaluator: The plan documents five error categories with distinct "Exit with non-zero" patterns, but no requirement assigns unique exit codes. Monitoring systems (Docker health checks, orchestration restart policies, log shippers) cannot distinguish a root-refusal failure from a missing su-exec failure programmatically. Using exit code 1 for all failure modes reduces automation potential and makes incident triage slower. -->

- [ ] CHK012 Does the spec require logging which privilege-drop tool (su-exec vs gosu) was resolved at runtime, giving operators visibility into which code path is executing for security auditing? [Debuggability, §OR-005, §AD-001] <!-- Evaluator: AD-001 documents a fallback from su-exec to gosu, but no requirement mandates logging which tool was selected. An operator troubleshooting a signal propagation issue (gosu vs su-exec may behave differently for groups, capabilities, or signal forwarding per the spec's own operational constraints) cannot determine from logs which tool is in use. A security auditor examining the running container would have no evidence of which privilege-drop tool executed. -->

## Operator Debuggability

- [ ] CHK013 Are the chown target paths logged at startup so operators can verify that the correct volumes are being chowned, especially when the filesystem layout or volume mounts are customized? [Debuggability, §OR-004] <!-- Evaluator: OR-004 mandates chown of /app/data and /app/modules but does not require logging the paths being chowned. An operator using custom bind mounts, symlinks, or additional volumes has no startup confirmation of which paths were processed. A log line like "chown -R --no-dereference /app/data to UID 1001:GID 1001" would confirm the operation scope. -->

- [ ] CHK014 When UID/GID reuse occurs (existing user already has the target UID), does the spec require logging the matched user's name, shell, and home directory to help operators debug unexpected identity behavior? [Debuggability, §Spec §Edge Cases] <!-- Evaluator: The edge cases specify reusing the existing user entry and confirming a valid shell and home directory, but no requirement logs which user was matched. An operator who expects username "app" but the system reused a different username (e.g., "nobody") for the same UID has no log output indicating the actual username in use. This mismatch could silently break application assumptions about the home directory or shell. -->

- [ ] CHK015 Is a startup audit trail of env var resolution (which vars were explicitly set, which defaulted, what fallback was applied) emitted before any destructive operation (user creation, chown) so operators can correlate startup identity with container behavior? [Debuggability, §OR-001, §OR-002, §OR-006] <!-- Evaluator: OR-001 and OR-002 define env var resolution but no requirement logs the resolved values. If an operator sets PUID=foo (non-numeric fallback to 1000) and PGID=1001, the warning on PUID does not include the final resolved UID, leaving ambiguity about which value was actually used. An audit trail printed before destructive operations would let operators verify the identity configuration before it takes effect. -->

- [ ] CHK016 Does the spec require the entrypoint to emit a successful-startup marker log line after privilege drop but before exec, allowing operators to confirm the entrypoint completed before the CMD takes over? [Operability, §Plan HINT-001] <!-- Evaluator: HINT-001 prescribes a strict order of operations (trap → read → validate → create → chown → exec). Without a marker log line like "entrypoint complete, starting uvicorn via su-exec", an operator seeing uvicorn output has no confirmation that the entrypoint's entire chain (especially chown) finished successfully before the CMD started. A missing marker could mask a silent failure in a late entrypoint phase. -->
