# Security Requirements Quality Checklist: PUID/PGID Entrypoint

**Domain**: Security | **Depth**: Standard | **Audience**: Reviewer
**Focus Areas**: Root Refusal Enforcement, Least-Privilege Privilege Drop, Volume Permission Handling, Secure Env Var Handling

---

## Root Refusal Enforcement

- [ ] CHK001 Does OR-003 specify the exact lifecycle enforcement point for root refusal (before user/group creation, before chown, before any filesystem writes) to prevent partial execution under UID/GID 0? [Completeness, Spec §Operational Requirements OR-003] <!-- Evaluator: OR-003 says "exit with a non-zero code and clear error message" but does not mandate when in the sequence the check occurs relative to user creation or chown. Plan HINT-001 implies order (validate → create → chown → exec) but the requirement itself is silent on enforcement timing. -->
- [ ] CHK002 Is the PGID=0 refusal case independently testable with its own verification criterion, or is it conflated under the PUID=0 test alone? [Testability, Spec §Operational Objectives OBJ-1 Verification Criterion 3] <!-- Evaluator: VC-3 only tests PUID=0. PGID=0 with PUID≠0 is a separate operational path (e.g., PUID=1001 PGID=0) that could grant root-group access on the host and is not independently verified. -->
- [ ] CHK003 Is the root refusal behavior consistent with the "fail-fast" error handling pattern defined in the plan without introducing an undocumented fallback, retry, or silent-default path? [Consistency, Spec §Operational Requirements OR-003 → Plan §Error Handling Strategy] <!-- Evaluator: Plan's Error Handling Strategy says PUID=0/PGID=0 → "Fail-fast: Exit with non-zero, clear error message. No retry." The spec OR-003 is consistent on exit but does not explicitly exclude silent continuation or warning-only behavior. -->

## Least-Privilege Privilege Drop

- [ ] CHK004 Is the temporary root execution window in the entrypoint (user/group creation and chown phase) acknowledged as a security tradeoff with an operator-facing runbook requirement to document the window? [Completeness, Spec §Compliance Check → Spec §Runbook Requirements] <!-- Evaluator: Compliance Check §IV acknowledges the root window as "accepted per linuxserver.io pattern" and says "runbook documents this window." However RR-001 only requires documenting how to set PUID/PGID in docker-compose.yml — there is no RR requiring documentation of the root window or its risk. -->
- [ ] CHK005 Does OR-005 require that the privilege drop tool (su-exec/gosu) drops all ambient Linux capabilities (not just UID/GID) to achieve true least-privilege execution for the uvicorn process? [Security, Spec §Operational Requirements OR-005] <!-- Evaluator: OR-005 mandates privilege drop via exec su-exec to ensure correct UID/GID and signal propagation, but does not mention Linux capabilities. Changing UID/GID alone does not clear all capabilities; if capabilities are inherited, the uvicorn process may retain more privilege than a traditional non-root USER directive. -->
- [ ] CHK006 Are the security properties of su-exec and gosu asserted as equivalent (capability drop behavior, signal propagation guarantee, working directory, environment preservation) without assuming undocumented behavior? [Consistency, Spec §Operational Requirements OR-005] <!-- Evaluator: OR-005 treats su-exec and gosu as interchangeable ("su-exec (or gosu if su-exec is absent)") but the spec does not verify they have identical security profiles. su-exec is ~25 KB and minimal; gosu is Ruby-based and may handle groups, capabilities, or signal forwarding differently. -->

## Volume Permission Handling

- [ ] CHK007 Does OR-004 distinguish the failure mode for chown failures on mounted data volumes (hard error) vs read-only rootfs (warning) to prevent silent permission escalation on host-mounted paths? [Clarity, Spec §Edge Cases & Boundaries → Spec §Operational Requirements OR-004] <!-- Evaluator: The Edge Cases section distinguishes "chown fails on data volumes → hard error" (per STF-005 resolution) from "read-only rootfs → warning." However OR-004 itself merely states "MUST chown -R ... on every container start" with no failure-mode differentiation. An implementer reading only the requirements section would miss this distinction. -->
- [ ] CHK008 Is the recursive chown path scope (/app/data, /app/modules) bounded with sufficient precision to prevent unintended ownership changes on unexpected paths, symlink targets, or hidden files within those directories? [Security, Spec §Operational Requirements OR-004] <!-- Evaluator: OR-004 specifies two concrete paths. However chown -R follows symlinks by default; if /app/data or /app/modules contain symlinks to system paths, ownership of those targets would be changed. The spec does not address symlink behavior or require --no-dereference flags. -->
- [ ] CHK009 Is the concurrent-container chown race condition (STF-009) reflected as a documented security limitation in the spec requirements, or does it only appear in the stress-test findings section? [Scope Control, Spec §Stress-Test Findings STF-009] <!-- Evaluator: STF-009 documents "Concurrent containers on same volume race on chown" as a v1 limitation with no lock mechanism. This is a security concern (TOCTOU / permission race) but is absent from the spec requirements, operational constraints, and assumptions sections. A reader who skips stress-test findings would assume mutual exclusion. -->

## Secure Env Var Handling

- [ ] CHK010 Does the input validation chain (non-numeric → fallback with warning, out-of-range → hard error with clear message) serve an explicit injection-prevention purpose before values reach useradd/groupadd or shell expansion? [Security, Spec §Edge Cases & Boundaries] <!-- Evaluator: The spec validates PUID/PGID for being numeric and in range, which incidentally prevents shell metacharacter injection into useradd/groupadd arguments. However the spec does not frame this validation as an injection-prevention control, leaving the security purpose implicit. -->
- [ ] CHK011 Is env var case sensitivity specified as an operational requirement (not just a clarification note) to prevent silent misconfiguration from lowercase, mixed-case, or misspelled variants? [Completeness, Spec §Operational Requirements OR-001 → Spec §Clarifications] <!-- Evaluator: STF-008 clarified that env vars are "case-sensitive, uppercase only." However OR-001 simply says "read PUID and PGID environment variables" without specifying case sensitivity. An implementer could silently accept lowercase variants, leading to a situation where both PUID and puid are set with different values. -->
- [ ] CHK012 Does the independent default behavior (OR-002) risk masking configuration errors that should be surfaced, and is this risk documented in the spec's assumptions or risks section? [Consistency, Spec §Operational Requirements OR-002 → Spec §Assumptions & Risks] <!-- Evaluator: OR-002 defaults each var independently to 1000 when absent. If an operator sets PUID=invalid (triggering warning+fallback to 1000) and leaves PGID absent (silent default to 1000), the container runs as 1000:1000 with only one warning. This could mask the misconfiguration. The Assumptions & Risks section does not address this masking risk. -->
